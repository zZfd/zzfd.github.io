很多人第一次认真读 JSON-RPC，是因为要看懂 MCP（模型上下文协议）——它的底层消息格式正是 JSON-RPC 2.0。但 JSON-RPC 本身是个独立、通用、跟 AI 毫无关系的老协议：它只回答一个极小的问题——**通信双方往 JSON 里塞消息时，必须带上哪几个固定的字段，才能在一条混乱的数据流里认出「谁在问、谁在答、答的是哪一问」**。

这篇把 JSON-RPC 2.0 单独讲透：它的四种消息、每个字段的语义、标准错误码，以及为什么「基于文本流的传输」几乎必然会选它。这是一份可以脱离 MCP 独立食用的协议速查。

## 一句话定位：它是「远程函数调用」的最小约定

JSON-RPC（JavaScript Object Notation Remote Procedure Call）是一个**无状态、轻量级的远程过程调用（RPC）协议**。RPC 的核心诉求是：让「调用远端的一个方法」看起来尽量像「调用本地的一个函数」——你给出方法名和参数，对方执行完把返回值给你。

JSON-RPC 做的，就是用 JSON 把这件事标准化。它**刻意不规定传输层**：你可以把这些 JSON 跑在 HTTP 上、TCP 上、WebSocket 上，甚至跑在进程的标准输入输出（STDIO）这种最原始的字节流上。协议只管「消息长什么样」，不管「消息怎么送」。这种传输无关性，正是它能被各种场景复用的原因。

目前通行的是 **JSON-RPC 2.0** 规范。它的全部内容，就是四种消息格式：**请求（Request）**、**成功响应（Success Response）**、**错误响应（Error Response）**、**通知（Notification）**。

## 1. 请求（Request）：我要调用你的一个方法

当一端想调用另一端的某个方法时，发送这个格式：

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "city": "Beijing" }
  },
  "id": 1
}
```

四个字段：

- **`jsonrpc`（必填）**：固定为 `"2.0"`，声明协议版本。缺了它就不是合法的 2.0 消息。
- **`method`（必填）**：字符串，要调用的方法名。
- **`params`（可选）**：传给该方法的参数，可以是对象 `{}` 或数组 `[]`。
- **`id`（必填）**：一个唯一标识符（整数或字符串）。**这是整个协议的灵魂**——对方回复时必须原样带回这个 `id`，调用方才能把「回复」和「当初的哪次请求」对上号。

`id` 之所以关键，是因为 RPC 天然是**异步、可并发**的：你可能同时发出去五个请求，回复回来时未必按顺序、甚至混在别的消息里。没有 `id`，你根本不知道这条 `result` 是回应哪一问的。

## 2. 成功响应（Success Response）：给你返回值

方法成功执行后，这样回：

```json
{
  "jsonrpc": "2.0",
  "result": {
    "temperature": "25C",
    "condition": "Sunny"
  },
  "id": 1
}
```

- **`jsonrpc`（必填）**：固定 `"2.0"`。
- **`result`（必填）**：方法执行成功的返回值，可以是任何合法 JSON 类型（对象、数组、字符串、数字……）。
- **`id`（必填）**：与触发它的那次 Request 的 `id` 完全一致。

一条硬规则：**一个响应里，`result` 和 `error` 绝不能同时出现**。成功就只有 `result`，失败就只有 `error`。这让接收方可以用「有没有 `error` 字段」来一刀切地判断成败。

## 3. 错误响应（Error Response）：出错了，而且出错也有规矩

参数不对、方法不存在、内部崩溃……只要执行失败，必须返回标准的错误结构：

```json
{
  "jsonrpc": "2.0",
  "error": {
    "code": -32602,
    "message": "Invalid params",
    "data": "City 'Beijing' not found in database."
  },
  "id": 1
}
```

- **`error`（必填）**：一个有严格内部结构的对象：
  - **`code`（必填）**：整数错误码。协议预留了一批标准码（见下表）。
  - **`message`（必填）**：简短的错误描述。
  - **`data`（可选）**：附加的详细信息（如堆栈、上下文），方便调试。
- **`id`（必填）**：同样要匹配原请求的 `id`。**特例**：如果连原请求的 `id` 都没能解析出来（比如收到一段根本不是合法 JSON 的乱码），这里可以填 `null`。

协议规定的标准错误码，值得记住：

| 错误码 | 含义 | 触发场景 |
|---|---|---|
| `-32700` | Parse error | 收到的根本不是合法 JSON |
| `-32600` | Invalid Request | JSON 合法，但不符合请求对象的结构 |
| `-32601` | Method not found | 请求了一个不存在的方法名 |
| `-32602` | Invalid params | 方法存在，但参数不对 |
| `-32603` | Internal error | 服务端内部异常 |
| `-32000` ~ `-32099` | Server error | 预留给实现方自定义的服务端错误 |

`-32000` 到 `-32099` 这段是**留给你自己用的**：业务层面的错误（鉴权失败、资源被锁、配额耗尽等）可以在这个区间里定义自己的码。而 `-32768` 到 `-32000` 之间的其余部分是协议保留区，不要占用。

## 4. 通知（Notification）：只告诉你一声，不用回

通知和请求几乎一模一样，**唯一的区别是没有 `id` 字段**：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/resources/updated",
  "params": {
    "uri": "file:///var/log/syslog.txt"
  }
}
```

没有 `id`，就是在明确告诉接收方：**「我只是通知你一件事，你听着就行，不要给我发 Response。」**

这个「没有 id = 不需要回复」的约定极其干净。它让协议在「一问一答」之外，多了一条**单向推送**的通道——用于「事件发生了」这类不需要确认的消息。典型如：服务端发现某个被订阅的数据源变了，主动推一条通知让对方重新拉取；或者一个长任务想上报进度。

## 为什么「文本流传输」几乎必然选 JSON-RPC

理解了这四种消息，就能明白它为什么特别适配 **STDIO（标准输入输出）** 这类场景——比如本地进程之间的通信，双方都在往同一个字节管道里不断「吐」字符串。

这种管道有个先天的混乱：**请求、响应、通知全都乱序混杂在一条流里**，没有天然的边界和配对关系。JSON-RPC 用两个极简的机制，在这团乱麻里建立起了秩序：

1. **强制的 `id` 配对**——任何请求都带 `id`，任何响应都原样带回，于是「乱序」不再是问题，靠 `id` 就能把每个回复精确对回它的请求。
2. **无 `id` 的通知**——把「不需要回复的单向消息」和「需要配对的请求」从格式上就区分开，接收方一眼就知道该不该应答。

再加上它**传输无关、结构极简、天然基于人类可读的 JSON**，实现成本极低、跨语言无障碍。所以当一个系统需要在一条双向流上做结构化的 RPC 时，JSON-RPC 2.0 几乎是默认答案——MCP 选它，正是这个道理。

> 说到底，JSON-RPC 2.0 的全部智慧就浓缩在两点：**用 `id` 把异步的一问一答绑定起来，用「有没有 `id`」区分「要回复的调用」和「不用回复的通知」。** 四种消息，一套秩序。
