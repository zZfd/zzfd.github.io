定了要做 BFF，紧接着的问题就是：一个聚合首页，到底该开一个 `/home` 把所有数据塞进去，还是拆成三个接口？这个问题几乎人人都会问，但它问错了——**它把「怎么切」框成了一道数量题（一个 vs 几个），而真正要决定的是「在哪儿下刀」。**

本文给一套和技术栈无关的方法：先用五把尺子去量每一块数据的固有属性，量出「属性指纹」相同的归一组、不同的分家；至于每组最后落成 REST、WebSocket 还是懒加载，是分完组之后自然掉出来的结果，不是分组的依据。

## 先扭正框架：聚合和拆分可以叠加

聚合（一个接口内并行扇出 + 部分失败降级）和拆分（多个接口）不是二选一，**它们可以叠加**：你先把页面切成几组，每一组内部该聚合的照样聚合。

所以正确的姿势是 **「先分组，后定实现」**，而不是反过来。如果你从实现往回想——「这块要分页吗？那块要不要上 WebSocket？」——切出来的边界一定是零散、拍脑袋的。先拿尺子量数据的固有属性，让边界从属性里浮出来。

默认动作是**合并**：能放进一个接口就放一个，省一次往返。只有当某块数据在下面某把尺子上和邻居「节奏不同」时，才把它切出去。

## 五把尺子

### ① 变化频率 / 新鲜度——它多久变一次？

**机理：一个聚合响应的可缓存性，等于它最易变成员的可缓存性。**

这是最容易被低估的一条。只要你往一个接口里塞进一块「每秒都在变」的数据，整个接口就永远不可缓存——哪怕同一个响应里 90% 的字段（用户概要、推荐位）本来都能缓存好几分钟，它们的可缓存性全被那一块最易变的数据拖没了。易变的数据是缓存的「污染源」，必须隔离出去。

### ② 延迟 + 首屏位置——它快还是慢？在折叠线以上还是以下？

**机理：单个接口的耗时，等于它最慢成员的耗时。**

一个接口并行扇出 N 个下游，它的响应时间由最慢的那个决定。如果某块数据又慢、又位于折叠线以下（用户要滚动才看得到），那它**没有资格占用首屏的时间预算**——把它留在首屏接口里，等于让用户为一块他还没看到的数据多等几百毫秒。

### ③ 刷新节奏——它会被独立地重新拉取吗？

**机理：绑在一起，就只能一起刷。**

如果两块数据的刷新周期不同，把它们焊在一个接口里就只能迁就最频繁的那个。你不会为了每秒刷新一次实时数值，把几乎不变的用户概要也跟着每秒重拉一遍。需要独立刷新节奏的，要独立的接口。

### ④ 复用范围——只有这一屏要，还是别的屏也要？

**机理：跨屏复用的数据，不该是某一屏的私有字段。**

像「未读消息红点」这种东西，几乎每个页面的角落都有。它就应该是一个全局的 `/badges` 接口，被所有屏共享，而不是被塞进首页接口当一个私有字段、然后在每个需要它的页面里重复实现一遍。

### ⑤ 一致性要求——这几块必须是同一时刻的快照吗？

注意：**前四把尺子都是「找到不同就切开」，唯独第五把方向相反，是「足够一致就必须合并」。**

**机理：某些数据之间存在「加起来要对得上」的硬约束。** 比如一个汇总指标，和构成它的那批明细项，必须取自同一瞬间的快照——否则用户会看到汇总和明细对不上的诡异画面。这种「跨服务 join + 强一致」的活，**必须在 BFF 的一个接口里一次算好**，绝不能让客户端分两次去拉、再自己在前端加起来（两次请求之间数据可能已经变了）。

**前四把把数据往外推，第五把把数据往里拽，它们互相拉扯——平衡点就是下刀的地方。**

## 一个 worked example

把上面五把尺子套到一个典型聚合首页的五块数据上，列成一张表，分组就「看」出来了——它是量出来的，不是想出来的：

| 数据块 | ①变化频率 | ②延迟/位置 | ③刷新 | ④复用 | ⑤一致性 |
|---|---|---|---|---|---|
| 概要指标 | 分钟级 | 快·首屏 | 随页 | 仅此屏 | **要和明细一致** |
| 明细列表（静态部分） | 分钟级 | 快·首屏 | 随页 | 仅此屏 | **要和概要一致** |
| 实时数值 | **每秒** | —— | **独立·秒级** | —— | 容忍短暂滞后 |
| 推荐流 | 天级 | **慢·折叠下** | 独立 | 仅此屏 | 无 |
| 消息红点 | 事件触发 | 快 | **独立轮询** | **全 App** | 无 |

读这张表，分组自然浮现：

- **概要指标 + 明细列表（静态）**：五把尺子几乎一致，且第⑤把一致性约束把它俩焊死 → 合进**同一个聚合接口** `GET /home/summary`，内部并行扇出、按关键/非关键降级。
- **实时数值**：①每秒变 + ③需要独立的秒级刷新 → **拆出去**。而「每秒推送」这个特征一旦确定，实现自然落到 WebSocket / SSE 推送，不是 REST 轮询。
- **推荐流**：②慢 + 折叠线以下 → 拆成 `/home/feed` **懒加载**，等用户滚动到了再拉。
- **红点**：④全 App 复用 + ③独立轮询 → 提成全局 `/badges`，根本不归首页。

> 关键：实现方式（REST / WS / 懒加载）是被尺子量出来的，不是一开始拍的。分组依据是数据的**固有属性**，和技术栈无关——换任何一个新页面，都能拿这五把尺子重新量一遍。

## 降级 vs 拆分：解决的是两件不同的事

这是最容易混的一对概念，必须分清：

- **区分关键/非关键 + 降级**，解决的是「**同一组内的成员可能失败**」。这几块本该一起出现在同一屏，但某个下游可能挂掉——于是容忍它缺席（某个指标显示 `--`、某块数据用上一次的缓存值兜底）。它们**节奏相同，只是可靠性不同**。
- **拆分接口**，解决的是「**不同块节奏不同**」。缓存周期、延迟、刷新频率、传输方式都不一样，不该挤在同一次请求里。

判断一块「慢 + 非关键」的数据该**留在聚合里降级**还是**拆出去懒加载**，支点是它落在折叠线的哪一侧：

- 在首屏可见区 → **留下来降级**：设一个紧超时（如 200ms），超了就返回空，不拖累首屏其它内容。
- 在折叠线以下 → **拆出去懒加载**：反正用户还没滚到，且懒加载时能从容拿到完整数据，而不是被超时砍成的空值。

## 中间路线：不拆，但流式返回

如果把一块内容拆出去的**唯一**理由是「它慢、会拖首屏」，其实还有第三条路：**单接口 + 流式渐进返回**（HTTP 分块 / SSE / 类似 GraphQL `@defer` 的机制）。一次请求、一个往返，快的部分先吐给客户端渲染首屏，慢的部分随后补流进来。

这条路在能力完整的运行环境（现代浏览器、原生 App）上很漂亮。但要诚实地承认它的边界：**部分受限的客户端运行环境对流式响应支持很弱**（某些嵌入式 WebView / 小程序容器没有 SSE、对分块响应支持有限，往往只剩 WebSocket 一条路且有额外约束）。所以流式是否可行，取决于你最弱的那个端——如果有端撑不住，多半还得退回「首屏 summary + 折叠下 feed 懒加载」的拆分方案。**这正是「实现被尺子量出来」的另一面：连传输方式都要被最弱端的能力反向约束。**

## 两个反模式

**别按微服务边界拆接口。** 给每个下游各配一个 BFF 接口（`/users`、`/list`、`/quotes`……让客户端自己去调 6 个），是最常见的错误。这等于把后端拓扑直接泄露给客户端，聚合的价值荡然无存，还把「部分失败怎么办」的编排重新推回给每个端各写一遍。**要按客户端的渲染 / 缓存 / 刷新需求切，不是按后端服务切。**

**也别走另一个极端，拿一个超级接口装下整个 App。** 那样会耦合一切、整体不可缓存、慢得跟最慢的那个成员一样——五把尺子里每一条都被它违反了。

## 一句话尺子

> **一起取、一起缓存、一起刷新、一起失败、且必须一致 → 合并进一个接口（内部并行扇出 + 降级）；这几条里任意一条分道扬镳 → 拆开。实现方式（REST / WebSocket / 懒加载 / 流式）是分完组后自然掉出来的，不是分组的依据。**
