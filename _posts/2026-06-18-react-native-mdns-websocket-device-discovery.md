很多场景需要让同一个局域网里的多台设备**零配置地互相发现、连接并实时通信**：没有公网、没有中心服务器、用户也不可能去手填 IP 和端口。设备一上线，就得自己「找到彼此」并稳定地连上。

这条链路其实是**两个相互独立的阶段**，必须严格区分开——这也是本文的主线：

1. **设备发现（Discovery）**：基于 **mDNS / DNS-SD** 的、无连接的服务发现。解决「网络里有哪些设备、它们在哪个地址」。
2. **设备通信（Communication）**：在发现得到的地址上，用 **WebSocket** 建立长连接做双向实时通信。解决「连上之后如何稳定、高效地收发消息」。

这两层用的是完全不同的网络模型，**绝不能混为一谈**：发现层是组播问答，没有「连接」、也没有严格的客户端/服务端；通信层才是连接导向的 C/S 模型。下面分别展开。

> 如果对 DNS / PTR / SRV / 多播 / 广播域这些底层概念有些生疏，可以先读这份两三分钟的速查垫底：《[计算机网络速查：读懂设备发现前要垫的几个底](/2026/06/18/network-basics-cheatsheet-for-device-discovery)》。

## 一、问题域与约束

先把约束摆清楚，因为后面所有设计都是被它们逼出来的：

- **零配置发现**：设备间不能依赖人工录入地址，必须自动发现。
- **无中心节点**：局域网内没有一台公认的服务器来做注册中心。
- **节点易变**：设备会上线、下线、休眠、被拿走、断网。「在线设备集合」是一个时刻在变的动态集合。
- **移动平台会回收连接**：移动操作系统在应用进入后台时会随时杀掉 socket，连接的「生」与「死」必须能被准确感知。
- **网络不可信**：弱网、丢包、抖动、AP 漫游都会发生。

一句话概括：**在一个没有中心、节点随时进出、网络随时抖动的环境里，维持一张实时可用的设备连接表。**

# 第一部分 · 设备发现：mDNS / DNS-SD

发现阶段要回答的问题只有一个：**「局域网里有哪些目标设备，它们各自的地址（host:port）和元数据是什么？」** 它不负责建立任何连接。

> 本文对发现层只做主线介绍。注册 / 监听的具体流程、注册与解析的失败处理、网络变更与前后台切换时如何重建，这些工程细节单独成篇：[《深入设备发现：mDNS 的注册、监听与异常 / 状态处理》](/2026/06/18/mdns-device-discovery-register-resolve-lifecycle)。

## 二、mDNS / DNS-SD 原理

设备发现的底层是 **mDNS（Multicast DNS）+ DNS-SD（DNS Service Discovery）**，也就是 Bonjour / Zeroconf 那一套。它的精髓是**去中心的组播问答**：网络里没有 DNS 服务器，谁想找服务，就往组播地址 **`224.0.0.251:5353`**（IPv4，IPv6 为 `ff02::fb`）发问，能提供该服务的设备直接组播应答。

这里**没有「连接」，也没有连接意义上的客户端/服务端**——它是一问一答的无连接广播。参与方的角色是按「发布 / 查询」划分的：

- **发布方（Advertiser / Publisher）**：把自己提供的服务**注册并广播**到局域网（announce）。
- **浏览方（Browser / Querier）**：组播**查询**某类服务，收集应答（browse）。

> 注意这组角色和后面通信层的「客户端/服务端」是**两套正交的概念**。通常是「将要提供通信服务的设备」去做发布方（好让别人找到它的地址），但发布/浏览本身只是发现层的分工，不要和 WebSocket 的 C/S 角色混在一起理解。

## 三、四类 DNS Record 的分工

服务信息由四类 DNS record 协作承载，理解它们的分工是用好 mDNS 的关键：

| Record | 职责 | 类比 |
|--------|------|------|
| **PTR** | 「这类服务有哪些实例」 | 服务的目录 / 黄页 |
| **SRV** | 某实例在哪台主机的哪个端口 | 地址簿里的「主机:端口」 |
| **TXT** | 实例的元数据键值对 | 名片上的备注 |
| **A / AAAA** | 主机名 → IP 地址 | DNS 的地址记录 |

一次完整的发现，就是浏览方通过 PTR 列出实例 → 用 SRV 拿到主机名和端口 → 用 A/AAAA 解析出 IP → 读 TXT 拿到元数据的过程。最终产物是一组 `(host, port, 元数据)`，交给第二阶段去建立连接。

**服务类型的命名约定**形如 `_<service>._tcp`（或 `._udp`），这是 DNS-SD 的规范格式。自定义服务应当注册一个专属的服务类型，以便和网络里其它无关服务区分开。

## 四、元数据设计：把筛选前置到 TXT

TXT record 是个常被低估的设计点。它允许在服务广播里携带一组**键值对元数据**，带来一个关键能力：**在「建立连接之前」就完成筛选**。

浏览方扫到一批服务实例时，可以直接读 TXT 里的元数据做判断，而**不必先逐个建连接、握手、再问一遍**。典型适合放进 TXT 的字段：

{% highlight text %}
协议 / 版本号    →  判断两端能否通信、是否需要降级
设备 / 实例标识  →  识别这是哪一个节点、用于去重
分组 / 命名空间  →  过滤掉「不属于本组」的设备
服务端口        →  动态端口场景下，把实际端口随广播带出（见第六节）
{% endhighlight %}

> 设计原则：**凡是「连接前就需要用来做决策」的信息，都应放进 TXT**；而真正的业务数据、敏感信息绝不放——TXT 是局域网内明文组播，任何人都能看到。把它当成一张「公开名片」来设计字段。

## 五、跨平台原生能力的统一抽象

mDNS 的发现/广播能力由各平台的系统框架提供，行为细节并不一致。在 React Native / 跨端这类场景里，**原生模块的核心价值，就是把这些差异封装在 native 层，对上只暴露一套平台无关的 JS 接口**。

各平台典型的原生能力：

- **Apple 平台**：Bonjour——经典的 `NSNetService` / `NSNetServiceBrowser`，或更现代的 Network framework（`NWListener` / `NWBrowser`）。
- **Android 平台**：系统的 `NsdManager`（Network Service Discovery，底层即 DNS-SD）。

良好的封装应当把它们收敛成一套语义一致的接口，让上层只关心「发现了什么服务、它的地址和元数据」，而**完全不感知底层是 Bonjour 还是 NsdManager**：

{% highlight javascript %}
// 发现层的统一接口（示意）
// —— 发布方
startAdvertising(serviceType, port, txtMeta); // 注册并广播服务
stopAdvertising();

// —— 浏览方
startBrowsing(serviceType);                   // 组播查询
stopBrowsing();

// —— 事件
emitter.on('serviceFound', (svc) => { /* 解析 host:port + 元数据 */ });
emitter.on('serviceLost',  (svc) => { /* 标记离线 */ });
{% endhighlight %}

至此，发现阶段结束——我们拿到了目标设备的 `host:port` 与元数据。下面进入**完全不同的第二阶段**。

# 第二部分 · 设备通信：WebSocket

通信阶段要回答的是：**「拿到地址之后，如何在两台设备间建立一条稳定、高效、可双向收发的长连接？」** 这一层才是连接导向的，**这里才有严格的客户端 / 服务端（C/S）角色**。

## 六、通信层的 C/S 模型与动态端口

WebSocket 是一个明确的 C/S 协议：

- **WebSocket 服务端**：在某个端口上 `listen`，被动接受连接。
- **WebSocket 客户端**：用第一阶段发现到的 `host:port` 主动 `connect` 拨入。

通常**由 WebSocket 服务端那台设备担任发现层的发布方**——它先把自己的服务端口广播出去，客户端发现后才能拨进来。这就把两个阶段衔接了起来。

**服务端口不应写死**（如 `8080`），否则可能与设备上其它进程冲突。正确做法是把端口分配权交给操作系统：

1. 服务端 socket **绑定端口 `0`**；
2. 操作系统从 ephemeral 端口范围里**自动分配一个空闲端口**；
3. 通过 `getsockname` 把系统实际分配的端口**读回来**；
4. 把这个实际端口**写进 mDNS 广播**（SRV 的端口字段，或 TXT 元数据）——这正是第一阶段「服务端口」字段的来源。

{% highlight text %}
服务端 bind(0) → OS 分配 51843 → 写入 mDNS 广播 → 客户端发现后据此拨号
{% endhighlight %}

这样彻底规避了端口冲突，也不需要任何「约定端口」。两个阶段的衔接闭环如下：

{% highlight text %}
  [发现层]  发布方 announce  ──组播──▶  浏览方 browse → 拿到 host:port
                                              │
  [通信层]  WS 服务端 listen ◀──connect───  WS 客户端 dial(host:port)
                              握手 → 一条全双工长连接，消息靠 ID 关联
{% endhighlight %}

## 七、通信层要解决的核心问题（概览）

建连只是开始。一条长连接要在抖动的网络里长期可靠地服务，还要解决下面这些问题——每一项都不简单。这里只做概览，**完整的工程实现（含代码、踩坑与内存回收等细节）见独立深入篇**：[《深入设备通信：WebSocket 长连接的工程化实践》](/2026/06/18/websocket-device-communication-deep-dive)。

- **连接管理**：复用一条全双工长连接，用 `messageId` / `responseId` 关联请求-响应（这是「请求-响应关联」，不是「多路复用」——WebSocket 本就全双工）；连接表以稳定 `deviceId` 为键；重连时旧连接要连同心跳定时器、事件监听一起**彻底销毁**，否则漏内存。
- **消息可靠性**：`send()` 返回 ≠ 对端收到。要区分发送失败 / 响应超时 / 连接中断三种失败；每请求挂独立超时；**超时 ≠ 失败**，靠幂等 + 去重消化这层不确定性。
- **活性检测与重连**：多层兜底（应用层心跳为主 + mDNS goodbye + TCP keepalive 兜底）；重连用指数退避 + jitter 防重连风暴；区分「网络抖动」与「真掉线」。
- **生命周期管理**：移动系统进后台会杀 socket；前后台策略按设备形态权衡（手持设备断连重连，常驻设备保持存活）。
- **安全：鉴权 + 加密**：两个正交问题。握手阶段先鉴权（质询-应答 + 防重放）再放行业务消息；传输优先 TLS / `wss://`，密钥每设备一份且可轮换。

## 八、总结：两个阶段，一台状态机

回头看，这类系统真正的难点从来不是「让设备发现彼此」——mDNS 几行就能跑通。难的是把**发现**和**通信**两个阶段各自做扎实、再稳稳衔接起来：

- **发现层（mDNS / DNS-SD）**：去中心组播问答，发布/浏览角色，靠 TXT 把筛选前置，产物是 `(host, port, 元数据)`。
- **通信层（WebSocket）**：连接导向的 C/S，复用一条全双工长连接 + messageId/responseId 关联请求-响应、连接表以 deviceId 为键(含旧连接的彻底销毁)、消息级超时与重试、多层活性检测、退避重连、握手鉴权 + 按需加密。

几条可迁移的经验：

- **严格区分发现与通信两层**，不要把组播发现和连接导向的 C/S 混为一谈——这是理解整套方案的前提。
- **把通信链路收敛成一个显式状态机**（已发现 / 已连接 / 心跳中 / 重连中 / 已离线），而不是散落各处的回调，调试和排障会轻松一个数量级。
- **元数据前置到 TXT**，在连接前完成筛选，省掉大量无效连接。
- **连接表以稳定 deviceId 为键**，重连合并而非新建；旧连接要连同定时器、监听器一起彻底销毁。
- **消息不是 send 完就算数**：超时 ≠ 失败，靠每请求超时 + 幂等去重消化不确定性；失败原因要区分发送失败 / 响应超时 / 连接中断。
- **活性检测多层兜底**，以应用层心跳为主，退避一定要加 jitter。
- **安全拆成鉴权 + 加密两个正交问题**：握手阶段先鉴权(质询-应答 + 防重放)再放行，传输优先 TLS、密钥每设备一份且可轮换。
- **生命周期与安全都是「场景决定的权衡」**，认清假设、诚实标注边界，比追求教科书式的完美更有工程价值。
