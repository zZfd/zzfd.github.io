写《[深入设备通信：WebSocket 长连接的工程化实践](/2026/06/18/websocket-device-communication-deep-dive)》时,绕不开一个前置问题:**既然有 HTTP,为什么还需要 WebSocket?SSE 又是什么,什么时候够用?** 这篇就把「Web 实时通信」这条技术线索理清楚——它们底层几乎都是 TCP,真正的差别在**方向性**和**谁能主动发起**。理解了这条线,选型就不再靠感觉。

## 一、起点:HTTP 为什么做不了实时

**HTTP 基于 TCP**(HTTP/1.0、1.1、2 都是;HTTP/3 是例外,见第五节)。而 TCP 本身是**全双工**的——可同时双向收发。可问题不在传输层,在 HTTP 的**语义模型**:

> HTTP 严格是 **请求 → 响应**:**只能客户端发起,服务端不能主动开口**。服务端只能在收到请求后回一个响应,绝不能凭空向客户端推消息。

所以这里说的「单向」不是"数据只往一个方向流"(请求往上、响应往下,数据其实双向),而是**「发起权单向」——服务端无法主动推送**。这正是实时场景(消息、通知、行情、设备状态)的痛点。

为绕开它,社区演进出几条路线:

- **轮询(polling)**:客户端定时问"有新消息吗"。简单,但延迟高、空请求多、浪费。
- **长轮询(long-polling)**:服务端把请求**挂住**,有数据才回。比轮询好,但每收一条就得重新发起一次请求,仍是"伪推送"。
- **SSE**:真正的服务端单向推流(下一节)。
- **WebSocket**:一条连接上的全双工(第四节)。

## 二、SSE:基于 HTTP 的单向服务端推送

**SSE(Server-Sent Events)基于 HTTP,所以也是 TCP。** 它没发明新协议——本质就是**一个一直不关闭的 HTTP 响应**:客户端发一个普通 GET,服务端回 `Content-Type: text/event-stream`,然后**把响应体一直开着,源源不断往里写事件**。

{% highlight text %}
客户端 ──GET──▶ 服务端
       ◀── 200 OK, Content-Type: text/event-stream（响应不关闭）
       ◀── data: {...}\n\n      （服务端随时往下推）
       ◀── data: {...}\n\n
       ◀── ……
{% endhighlight %}

**为什么 SSE 也是「单向」?** 和 HTTP 的单向含义不同:

> SSE 是**纯粹的「服务端 → 客户端」推流**。服务端能往下推了(补上了 HTTP 缺的那块),但这条通道**只能往下走**——客户端无法用它向服务端发数据;客户端要发东西,只能**另开普通 HTTP 请求**。

SSE 的其它特点:

- **自带断线自动重连**:浏览器的 `EventSource` 断线后会自动重连,并用 `Last-Event-ID` 续传(配合服务端的事件 `id` / `retry` 字段)。
- **只能传 UTF-8 文本**:要传二进制得自己编码(如 base64)。
- **实现极轻**:服务端就是个长开的 HTTP 响应,无需特殊协议栈。

**SSE 最大的坑——连接数限制:**

| 走的协议 | 并发上限 |
|----------|----------|
| **HTTP/1.1** | **每域名约 6 条**(浏览器硬限制),且**跨标签页共享** |
| **HTTP/2 / HTTP/3** | 多路复用到一条连接,受**最大并发流数**约束(默认常见 **100**,可配) |

HTTP/1.1 下这个 **6** 尤其致命:每条 SSE 是长期占用的连接,同一站点多开几个标签页、每页连一条,**6 个名额很快占满**,之后连**普通 HTTP 请求都会被阻塞**。所以实践中通常**每个应用只维持一条 SSE**,所有事件通过它按 `type` 分发,而不是为每个功能各开一条。

## 三、WebSocket:一条连接上的全双工

**WebSocket 基于 TCP**,通过 **HTTP Upgrade 握手**从一条 HTTP 连接"升级"而来,之后双方按**帧(frame)**收发,文本/二进制都行,**两端都能随时主动发**——这才是真正的全双工。

它补上了 SSE 缺的"上行":不再需要"下行用 SSE、上行另开 HTTP"那种割裂。代价是比 SSE 重一些(独立协议、要管连接生命周期/心跳/重连)。

> WebSocket 本身的协议细节、握手过程、各平台用法与工程实践,见《[深入设备通信:WebSocket 长连接的工程化实践](/2026/06/18/websocket-device-communication-deep-dive)》的「前置」与正文。

## 四、HTTP/2 与 HTTP/3·QUIC:为什么 HTTP/3 改用 UDP

上面多次提到"HTTP/2+ 能多路复用、解除 6 连接限制",这背后是 HTTP 传输层的两次大变革。

**HTTP/2:多路复用,但被 TCP 拖住。** HTTP/2 把多条流复用到**一条 TCP 连接**上,解除了"每域名 6 连接"的瓶颈。但它被 **TCP 队头阻塞(Head-of-Line blocking)** 拖累:TCP 保证字节严格按序到达,**只要丢一个包,后面所有流都得卡住等重传**,哪怕它们和丢包毫无关系。HTTP/2 解决了应用层 HoL,却解决不了传输层的。

**HTTP/3:把传输换成 QUIC,而 QUIC 跑在 UDP 上。** 注意——**不是图 UDP 的"不可靠",而是要逃离 TCP**。可靠、有序、拥塞控制,QUIC 全部在**用户态自己重新实现**,UDP 只是最薄的"搬运层"。改用 UDP 解决四件事:

1. **消灭传输层队头阻塞**:QUIC 的每条流**独立确认、独立重传**,一条流丢包不连累其它流。要做到这点就不能再用 TCP(TCP 行为焊死在内核里)。
2. **握手更快**:QUIC 把传输握手和 **TLS 1.3** 加密握手合一,新连接 1-RTT、恢复连接 0-RTT(加密是内建的)。
3. **连接迁移**:TCP 连接由四元组标识,**IP 一变(WiFi 切蜂窝)就断**;QUIC 用独立的 **Connection ID** 标识,网络切换不断连——对移动设备很关键。
4. **抗中间设备僵化**:QUIC 几乎把传输头也加密,NAT/防火墙改不了;且随浏览器/应用发版升级(用户态),不必等内核更新。

> 为什么偏选 UDP?因为它是"**IP + 端口**"这层最薄、最通用、能穿 NAT 的底座,没有 TCP 的有序/可靠包袱,正好让 QUIC 在其上自由搭一套更好的传输。(不用裸 IP 是因为需要 root 且常被封。)

## 五、选型对比与建议

| | 传输 | 方向性 | 谁能主动发起 | 数据类型 |
|---|------|--------|------------|----------|
| **HTTP(轮询/长轮询)** | TCP(/QUIC) | 数据双向,但发起权单向 | 仅客户端 | 文本/二进制 |
| **SSE** | HTTP → TCP | **单向:服务端 → 客户端** | 服务端推;客户端回话另开请求 | 仅 UTF-8 文本 |
| **WebSocket** | TCP(HTTP 握手) | **全双工** | 两端皆可 | 文本/二进制 |

怎么选:

- **只需服务端单向推**(通知、行情、进度、日志流):**优先 SSE**——更轻、自带重连、走标准 HTTP 基础设施;HTTP/2+ 下也无连接数顾虑。
- **需要双向、低延迟、二进制**(聊天、协同编辑、游戏、**设备间互发指令**):**用 WebSocket**。
- **能简单别上复杂**:别为一个"偶尔拉一下"的需求上 WebSocket;也别用一堆长轮询硬扛本该用 SSE/WebSocket 的实时场景。
- **底层尽量用 HTTP/2 或 HTTP/3**:多路复用能解除 SSE 的 6 连接限制,HTTP/3·QUIC 还能解决移动端的弱网与连接迁移。

一条线索收尾:**HTTP 不能服务端推 → SSE 补上单向推 → WebSocket 做到全双工;而 HTTP/2 多路复用、HTTP/3 换 QUIC,是在传输层把这些方案的瓶颈进一步抹平。** 它们底层几乎都是 TCP,真正要分清的,永远是**方向性**和**发起权**。
