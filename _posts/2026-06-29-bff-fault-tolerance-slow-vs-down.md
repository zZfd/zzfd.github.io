先讲一个真实形状的故障，几乎每个做过 Node 聚合层的人迟早会撞上它。

## 故障现场

一个聚合首页接口 `GET /home/summary`，内部并行扇出调好几个下游。其中营销服务是**非关键**下游，你早就用 `Promise.allSettled` 给它做了降级——失败就返回空 banner。看起来万无一失。

某天凌晨三点：

- 整个首页 **P99 从 200ms 飙到 8 秒**，大量用户白屏、转圈、超时。
- 账户、列表、计算服务**全部正常**。
- 只有营销服务**变慢了**——它**没挂、没报错**，响应从 50ms 涨到 8 秒，但最终还是规规矩矩返回 200。

问题来了：一个**「非关键、且已经做了降级」**的下游，仅仅是**变慢**（没挂），凭什么把整个首页拖垮？

要回答这个问题，得先理解 Node 的运行模型，以及一类专门坑 Node 的故障：**资源耗尽型级联**。

## 题眼：Node 不是「一请求一线程」

很多人脑子里的并发模型是「一请求一线程」（Java / Go 的直觉）：一个线程卡住，只卡它自己，别人不受影响。**Node 完全不是这样。**

Node 是**单线程事件循环**处理所有 JS，成千上万的并发请求跑在同一个线程上。它能扛高并发，靠的不是多线程，而是**「没人傻等」**：遇到 I/O 就 `await` 挂起、把线程让出去给别人。一句话点死它的命根子：

> **没有任何一个请求可以「占着线程干等」，所有等待都必须是「挂起让位」式的。**

`await fetch(营销)` 确实挂起让位了，线程没被它占住。**但「线程没被占住」绝不等于「什么都没被占住」。** 这是整个故障的认知盲区。

### 一个请求卡 8 秒，赖着不放的到底是什么

`await fetch(营销)` 挂起的那一瞬间，这个请求的整个上下文悬在半空，持续占用着：

- **一个出站 socket / 连接池里的一条连接**（连营销那条）——响应没回来，这条连接不能还。
- **入站那条 HTTP 连接**（客户端到 BFF 的）——首页还没拼完，不能关。
- **内存里这个请求的全部上下文**——闭包、已经拿回来的其它下游数据、待执行的回调。
- **事件循环里一个待决回调。**

线程是让出去了，但上面这些**进程级的有限资源**，一样都没释放。

### 「一个慢」如何被放大成「全站雪崩」

算一笔账（用一个 500 rps 的接口举例）：

- **正常时**，营销 50ms 返回。任意一刻悬在半空等营销的请求数 ≈ `500/s × 0.05s = 25` 个，毫无压力。
- **变慢到 8 秒后**，同样 500/s 涌进来，每个都要赖 8 秒才走。悬在半空的请求数 ≈ `500/s × 8s = 4000` 个，而且持续往上堆。

这 4000+「僵尸请求」虽然没占线程，却把**有限的进程级共享资源**一个个抽干：

1. **连接池先爆。** 连营销的 HTTP 连接池（假设上限 100）瞬间被占满，第 101 个请求卡在「等一条空闲连接」上，**它甚至还没发出请求**。
2. **入站侧被撑满。** 4000 个请求各攥一条「客户端到 BFF」的连接，**文件描述符（fd）和入站连接数**见底。
3. **内存爬升，GC 雪上加霜。** 4000 个上下文悬在堆上，内存上涨触发频繁 GC，GC 又拖慢一切——正反馈。
4. **新用户彻底进不来。** 一个全新请求第一步要去调账户服务，可此时连接池、fd、内存全被「等营销的僵尸」占满，**它连给账户服务发请求的资源都申请不到**。

最毒的地方在这：**账户、列表、计算服务从头到尾健康，但新用户连碰都碰不到它们了。** 一个非关键下游的「慢」，通过**全进程共享的有限资源**这条暗道，把整个 BFF 进程对所有用户拖瘫。

这个现象有名字：**资源耗尽型级联故障（cascading failure）**，这条具体路径常被叫**连接池耗尽**；而源头——一个慢依赖把上游资源占住——就是经典的 **slow dependency / head-of-line blocking**。Node 的少线程模型让它对「请求堆积」格外脆弱，因为它没有「一请求一线程」那种物理隔离。

### 慢 vs 挂，一句话钉死

把「挂」和「慢」并排放，差异触目惊心：

- **挂（快速失败）：** 营销一连接就 `ECONNREFUSED`，请求 5ms 内拿到失败终态，立刻释放资源走人，降级接管。资源占用 ≈ 0。
- **慢（迟迟不失败）：** 营销赖着资源 8 秒才给终态。占用时间是挂掉的 **1600 倍**，请求像血栓一样堆积，堵死共享池。

> **快速失败是系统的安全阀；一个「慢而不挂」的依赖，等于把安全阀焊死了。**

理解了这一点，容错的设计目标就清楚了：**核心不是「处理错误」，而是「把慢，强行变回快速失败，并阻止它堆积」。** 这正是下面四层防御要干的事。

## 四层防御

### ① 超时（timeout）：把「慢」强行变成「失败」

超时的唯一使命：把「慢」转成「快速失败」，让降级有机会触发。**没有超时，「慢」永远不会变成「失败」，你写的降级逻辑永远不会被调用。** 开头那个 `allSettled` 没救场，根子就在这——它只写了降级，却没有超时去制造「失败」这个触发条件。

**但这里有个致命的坑：到点必须真正取消底层请求、把 socket 还回池。**

```js
// ✅ 正确:AbortSignal.timeout 到点会真正 abort 底层 socket,释放连接
const res = await fetch(url, { signal: AbortSignal.timeout(500) });

// ❌ 假超时:Promise.race 看起来 500ms 就返回了,
// 但底层那个 fetch 根本没被取消,socket 照样被占满 8 秒!
await Promise.race([fetch(url), rejectAfter(500)]);
```

`Promise.race` 只是让**你的代码**以为超时了，可**底层连接根本没被释放**——你以为挡住了雪崩，实际那条 socket 还在傻傻耗满 8 秒。**超时的本质是「释放资源」，一个不取消底层请求的超时，等于没加。**

参数怎么定：按每个下游的 **p99 + 余量**单独设（营销 p99 50ms → 设 300~500ms），**不要**用一个巨大的全局超时去糊弄所有下游。

它的局限：就算每个都 500ms 超时，`500 rps × 0.5s = 250` 个并发仍然卡在那 500ms 上。超时只是**缩短**了占用，并没有**消除**占用——所以它只是第一层。

### ② 熔断（circuit breaker）：有记忆，踩过坑就不让后面的人再踩

类比就藏在名字里：配电箱里的**空气开关**。电流持续过载就**跳闸**断电、保护房子，过一阵再**试探性合闸**。

它和超时的本质区别是：**它有记忆。** 超时是「每个请求各自吃一次亏」（250 个并发各等各的 500ms）；熔断是「**有一批请求吃过亏后，就不让后面的再吃**」——失败率一旦超过阈值就跳闸，后续请求根本不发给营销、直接走降级。这就是它治雪崩的关键：跳闸之后，那 250 个本该卡在营销连接池上的请求**压根不会产生**，营销那个池的占用瞬间归零，从**源头**掐断占用。

它的核心是一个**三状态机**：

| 状态 | 行为 | 转移条件 |
|---|---|---|
| 关闭 Closed | 正常放行，统计失败率 | 失败率超阈值 → 打开 |
| 打开 Open | 快速失败 / 直接走降级，**不碰下游** | 冷却时间到 → 半开 |
| 半开 Half-Open | 放行少量试探请求 | 试探成功 → 关闭；失败 → 打开 |

**Half-Open 是精髓：它让系统在下游恢复后自动合闸，不需要有人半夜爬起来手动重启。**

实现上，社区有现成的库（如 `opossum`）把超时 + 熔断 + 降级打包在一起：

```js
import CircuitBreaker from 'opossum';

const breaker = new CircuitBreaker(callMarketing, {
  timeout: 500,                 // 内置超时:500ms 没回就算一次失败
  errorThresholdPercentage: 50, // 窗口内失败率 > 50% → 跳闸(Closed→Open)
  resetTimeout: 10_000,         // 跳闸后 10s 进入 Half-Open 试探
  volumeThreshold: 20,          // 窗口内至少 20 个请求才统计(防低流量误判)
});
breaker.fallback(() => ({ banners: [] })); // 降级:Open 态或失败时直接返回空 banner

const data = await breaker.fire(userId);   // Open 态时,这行根本不碰营销,直接给 fallback
```

`volumeThreshold` 这个参数容易被忽略却很重要：没有它，低流量时「来 1 个失败 1 个」就是 100% 失败率，熔断器会被误判成需要跳闸。

### ③ 隔离（bulkhead）：给每个下游独立的舱

类比：轮船的**水密舱壁**。一个舱破了，水漫不到全船。

做法是给每个下游**单独一套资源配额**（独立的连接池 / 独立的并发上限）。营销把它自己那套占满了，**账户、列表用的是另一套池子，永远抽不到它们头上**。它把「全进程共享资源 = 病毒传播路径」这件事**物理切断**，是对症下药的一层。

第一层，每个下游独立连接池：

```js
import { Agent } from 'undici';

// 营销专用舱:最多 50 条连接,占满也只占满这 50
const marketingAgent = new Agent({ connections: 50, keepAliveTimeout: 10_000 });
// 账户专用舱:独立的 100 条,和营销互不干扰
const accountAgent = new Agent({ connections: 100, keepAliveTimeout: 10_000 });

await fetch(marketingUrl, { dispatcher: marketingAgent, signal: AbortSignal.timeout(500) });
```

第二层（可选），应用层并发上限：

```js
import pLimit from 'p-limit';
const marketingLimit = pLimit(20); // 营销最多 20 个在途
await marketingLimit(() => callMarketing(userId));
```

这里有个坑：`p-limit` 满了之后是**排队**，而**队列本身也是一种资源**——无限排队等于换个地方继续堆积。真正的 bulkhead 语义应该是「满了就立即放弃、走降级」。实践中，**独立连接池 + 熔断**通常就够用了，并发上限是给特别需要硬隔离的关键路径额外加的保险。

### ④ 降级（fallback）：备胎，但它是最后一道

前三层把「慢」挡成了「快速失败 / 直接跳过」，降级负责**接住**这些失败、返回一个可接受的替代品。常见形态：静态默认值（空 banner）、上一次的缓存值（实时数据挂了用上次的值）、降质结果（个性化推荐挂了，返回一个通用热门兜底列表）。

多个下游聚合时，用 `allSettled` 兜住部分失败：

```js
const [acc, list, mkt] = await Promise.allSettled([
  accountBreaker.fire(uid),
  listBreaker.fire(uid),
  marketingBreaker.fire(uid), // 它内部已 fallback,这里基本不会 rejected
]);
```

降级有三个**一定要说**的坑：

1. **降级逻辑必须本地、便宜、可靠。** 别让兜底再去调另一个会抖的服务——**一个会失败的兜底，不叫兜底。**
2. **只给非关键下游降级。** 账户是关键下游，**绝不能给它一个「假装成功」的兜底**（返回空账户会吓死用户）。关键下游的正确处理是：用熔断让它快速失败，然后**整页明确报错**。
3. **降级只有在前三层生效后才轮得到它。** 没有超时把「慢」转成「失败」，降级永远不会触发——这就是开头那个 `allSettled` 没救场的全部原因：只写了第 4 层，前 3 层全缺。

## 组合顺序与统一客户端

四层的包裹顺序是固定的——**降级在最外层（catch 一切），熔断包着真正的调用，调用自带超时、且跑在自己的隔离池上**：

```
fallback( breaker( timeout( call_on_bulkhead_pool ) ) )
```

把它封装成一个工厂，每个下游建一个实例，各自带自己的池、自己的熔断器：

```js
import CircuitBreaker from 'opossum';
import { Agent } from 'undici';

function createClient({ name, baseUrl, timeout, poolSize, fallback }) {
  const agent = new Agent({ connections: poolSize, keepAliveTimeout: 10_000 }); // 隔离

  async function call(path) {
    const res = await fetch(baseUrl + path, {
      dispatcher: agent,
      signal: AbortSignal.timeout(timeout), // 超时:真正 abort,释放连接
    });
    if (!res.ok) throw new Error(`${name} ${res.status}`);
    return res.json();
  }

  const breaker = new CircuitBreaker(call, {        // 熔断
    timeout: timeout + 100,
    errorThresholdPercentage: 50,
    resetTimeout: 10_000,
    volumeThreshold: 20,
  });
  if (fallback !== undefined) breaker.fallback(() => fallback); // 降级(关键下游不给)

  return (path) => breaker.fire(path);
}

// 非关键:给兜底
const marketing = createClient({ name: 'marketing', baseUrl: MKT, timeout: 500, poolSize: 50, fallback: { banners: [] } });
// 关键:不给兜底,让它快速失败、整页明确报错
const account  = createClient({ name: 'account',  baseUrl: ACC, timeout: 800, poolSize: 100 });
```

## 每层切的是级联链上的哪一环

四层不是堆叠的冗余，而是各自掐断级联链上的不同环节：

- **超时** → 把「赖 8 秒」砍成「赖 500ms」，**缩短**单请求的占用时长。
- **隔离** → 营销占满的只是它自己那 50 条，**物理切断**共享传播路径。
- **熔断** → 跳闸后请求根本不进营销链，**从源头**让占用归零（治雪崩的主力）。
- **降级** → 把前三层造出的「快速失败」**翻译**成空 banner，让用户无感。

还有一个常见误解要澄清：**客户端超时救不了进程级雪崩。** 客户端 3 秒断开，是**用户体验自保**；但 BFF 进程里那个请求还在赖着营销 8 秒，资源照占不误——所以客户端超时对服务端的资源耗尽**毫无帮助**。容错必须做在 BFF 自己身上。

## 一句话锁死

> **在 Node 里杀死你的，从来不是「下游挂了」，而是「下游慢而不挂」——它让请求赖在共享的进程级资源（连接池 / fd / 内存）上不释放，堆积成资源耗尽型级联故障。防御的本质是两件事：缩短占用（超时）、切断共享（熔断 + 隔离）；降级只是最后的收尾。**
