「响应式」这个词在 Web 时代被用滥了，搬到 React Native（乃至任意跨端方案）后，很多人下意识地把它理解成「把设计稿等比缩放到不同屏幕」。但真正动手时会发现，直接给 `width`、`fontSize`、`padding` 写死数字，换台设备就和设计稿对不上——于是有人去找「缩放库」，把所有数字乘一个系数。

这条路不一定错，但**在选工具之前，得先想清楚响应式到底在对抗什么**。本文从第一性原理出发，依次讲透三件事：

1. 响应式真正要应对的**变化轴**有哪些，哪些其实平台已经替你兜底了；
2. **媒体查询的本质**——它为什么不依赖 CSS，又如何在没有浏览器的原生环境里实现；
3. **「自适应」与「等比缩放」两种哲学**的根本区别和各自的适用场景。

读完你应该能对「该不该引入缩放库」给出有依据的判断，而不是跟风。

## 一、先拆变化轴：响应式在对抗什么

把「响应式」笼统当成一件事，是大多数混乱的根源。它其实是**三个相互独立的变化轴**，每个轴的处理方式完全不同：

| 变化轴 | 含义 | 谁来处理 |
|---|---|---|
| **像素密度** | 同样物理尺寸的屏，塞进的物理像素数不同（1x / 2x / 3x） | **平台兜底**，不该进业务代码 |
| **屏幕物理尺寸** | 小手机 / 大手机 / 平板 / 桌面，可用宽高不同 | **你要处理**，响应式的主战场 |
| **字体无障碍缩放** | 用户在系统里调「更大字体」 | **平台默认开启**，你需要知道它存在 |

很多人把这三件事搅在一起，最典型的误解就是「直接写数字在不同**像素密度**上会不一致」。要破除它，先得理解尺寸单位。

## 二、第一性原理：dp —— 像素密度不该进你的代码

跨端框架里你写的 `width: 100`，单位**不是物理像素，而是「密度无关像素」**（dp / dip，density-independent pixel，Web 上对应 CSS px）。

它的定义是：**框架在渲染时，会把 dp 乘以设备的像素密度（PixelRatio），换算成物理像素。**

{% highlight text %}
物理像素 = dp × 设备像素密度(PixelRatio)

  width = 100dp 在 2x 屏 → 渲染 200 物理像素
  width = 100dp 在 3x 屏 → 渲染 300 物理像素
                ↑ 物理尺寸（毫米）几乎一致，肉眼看一样大
{% endhighlight %}

**结论：像素密度这个轴，平台已经替你抹平了。** 一个 `100dp` 的方块，在 2x 和 3x 屏上的**物理大小基本相同**，只是后者更清晰。你完全不需要、也不应该为「密度」去乘任何系数——那等于把平台已经做过的事再做一遍，只会出错。

> 同理，字号单位在原生侧近似 Web 的 `sp`：它在 dp 的基础上，**额外受系统「字体大小」无障碍设置影响**。默认是开启的，意味着用户调大系统字体时，你的文字会跟着变大。这是个**特性**而非 bug——除非有极强理由，不要全局关掉它，否则会伤害可读性与无障碍。

把密度和无障碍这两个轴排除后，响应式真正剩下的、需要你写代码去应对的，**只有「屏幕物理尺寸」一个轴**：设计稿通常按某个基准宽度（如 375）绘制，到了更宽或更窄的屏幕上，固定 dp 的元素与留白比例就会偏离稿子。这才是后文所有方案的靶心。

## 三、媒体查询的本质：一个纯函数，不依赖 CSS

应对屏幕尺寸差异的核心工具是**媒体查询（media query）**。但「媒体查询」常被误以为「必须配合 CSS 才生效」。要害在于分清两个独立的东西。

### 查询「语法」与查询「消费者」是两回事

`(min-width: 768px)` 这种写法，是 CSS Media Queries 规范定义的**语法**。但「使用这套语法」不等于「依赖 CSS 规则」。这套语法有**两个互相独立的消费者**：

| 消费者 | 作用 | 是否需要 CSS 规则存在 |
|---|---|---|
| CSS 的 `@media (...) { ... }` | 让**样式**在条件满足时生效 | 它本身就是 CSS |
| JS 的 `matchMedia(...)` | 在**脚本里**拿到布尔值 / 监听变化 | **不需要** |

### matchMedia 是个纯函数

把平台 API 的外壳剥掉，媒体查询匹配的本质是一个**纯计算**：

{% highlight text %}
matches(查询字符串, 当前环境状态) → boolean

  环境状态 = { 视口宽, 视口高, 方向, 像素密度, 颜色偏好, ... }
{% endhighlight %}

它做的事，仅仅是「把查询字符串拿去和当前环境状态比对，返回真假」。它**不读你的样式表**，页面里一条 `@media` 规则都没有，它照样工作：

{% highlight js %}
// 即使页面没有任何 @media 规则，这段也正常返回
const mql = matchMedia('(min-width: 768px)');
console.log(mql.matches);            // true / false，取决于当前视口宽度
mql.addEventListener('change', e => {
  console.log('跨过 768px 阈值:', e.matches);
});
{% endhighlight %}

记住这个本质——**「查询字符串 vs 环境状态 → 布尔值」**——下一节就能立刻明白：为什么在根本没有 CSS、没有浏览器的原生环境里，媒体查询也能跑起来。

## 四、一套断点，两条实现路径

成熟的跨端样式框架，通常让你**只定义一套断点**，然后在不同平台上用各自最优的手段去执行。开发者写的是同一份代码，底层却分成两条路。

{% highlight text %}
定义一套断点： { gtMd: { minWidth: 768 }, ... }
        │
        ├──  Web 端  ─────────────────────────────────
        │     · 样式：编译期提取成真正的 CSS @media 规则
        │       —— 交给浏览器引擎匹配，零运行时、SSR 安全、无重渲染
        │     · 逻辑：matchMedia 直接用浏览器原生 API
        │
        └──  原生端 ──────────────────────────────────
              · 没有 CSS / @media，用 Dimensions 拿视口尺寸
              · 用查询解析器把断点字符串和尺寸比对，模拟出 matchMedia
              · 尺寸变化时（屏幕旋转等）重新计算、通知订阅者
{% endhighlight %}

### Web 端：尽量编译成 CSS

Web 上最优解是**编译期**把响应式样式提取成原生 CSS `@media` 规则。这样匹配工作完全交给浏览器的 CSS 引擎：没有 JS 监听 resize、没有因尺寸变化触发的 React 重渲染、服务端渲染（SSR）也不会闪烁。这是「编译期路径」，性能最好。

只有当某段响应式逻辑**无法静态提取**（比如它参与了运行时的条件分支），才退回到运行时用 `matchMedia` 订阅。

### 原生端：用 Dimensions 模拟 matchMedia

原生没有 CSS、没有 `@media`、没有浏览器的 `matchMedia`。但因为上一节我们已经看清——媒体查询本质是个纯函数——于是它可以被**完全用 JS 实现**：

- 用平台的尺寸 API（`Dimensions` / `useWindowDimensions`）拿到当前视口宽高；
- 用一个查询解析器，把断点（`{ minWidth: 768 }`）和当前尺寸比对，算出布尔值；
- 监听尺寸变化（旋转、分屏），变化时重算并通知订阅方。

这样就「补」出了一个和浏览器 `matchMedia` 行为一致的实现。**上层逻辑因此可以完全不分平台**——它只管调 `matchMedia`，Web 由浏览器算，原生由 `Dimensions` 算。这就是「运行时路径」。

### 上层 hook 的统一设计：全局 store + 精准订阅

无论底层走哪条路，给组件用的「读当前断点」的 hook，通常是同一套经典结构，值得单独拎出来学习：

1. **全局单例 store**：整个应用只维护**一份**当前断点状态 `{ gtSm: true, gtMd: false, ... }`，由底层 `matchMedia` 的回调驱动更新。状态用不可变方式替换（每次 `{...}` 新对象），便于按引用比较。
2. **`useSyncExternalStore` 接入**：组件通过它订阅这个外部 store，这是 React 18 之后接入外部状态的标准范式，天然兼容并发与 SSR。
3. **用 Proxy 做依赖追踪，实现精准重渲染**——这是最精妙的一点：

{% highlight text %}
hook 返回的不是裸状态，而是包了一层 Proxy：
  读 media.gtMd 时，get 拦截器记下「这个组件用到了 gtMd」

之后只在「被读过的那些断点」发生变化时，才返回新引用、触发重渲染：
  组件只用了 gtMd → 仅当 sm↔md 越界时重渲染
                  → lg、xl 怎么变都不惊动它
{% endhighlight %}

它的思路和 Vue 的响应式、Valtio 等「按访问追踪依赖」的库同源：**你读了什么，才订阅什么**，从而把「任意断点变化导致全量组件重渲染」收敛成「只有相关组件才更新」。这是一个可以迁移到很多场景的通用模式。

## 五、两种哲学：自适应 vs 等比缩放

有了上面的机制，最后回到最初的纠结：到底该不该「把设计稿等比缩放」？这背后其实是**两种根本对立的设计哲学**。

### 一句话本质

| | 等比缩放 Scaling | 自适应 Adaptive / Responsive |
|---|---|---|
| 心智模型 | 把整张设计稿当一张图，按屏宽整体放大 / 缩小 | 尺寸固定，布局随空间流动 / 重排 |
| 类比 | 照片缩放（zoom） | 报纸排版（reflow） |
| 公式 | `实际值 = 设计值 × (屏宽 / 基准宽)` | `实际值 = 固定 dp`，靠 flex / 断点变布局 |

### 大屏上发生了什么

同一张「头像 + 文字」的卡片，从基准 375 宽换到更宽的屏：

{% highlight text %}
等比缩放：所有东西按 屏宽/375 放大
  [ ⬤(变大)   标题(变大字)            ]   ← 与稿子比例 100% 一致，只是整体"长胖"

自适应：尺寸不变，多出的空间用作留白或塞更多内容
  [ ⬤   标题(原字号)                   ]   ← 头像/字号和小屏一模一样
                              ↑ 多出的宽度→留白，或排下更多卡片
{% endhighlight %}

一句话：**缩放改变「元素本身的大小」，自适应改变「元素之间的关系与排布」。**

### 逐维度对比

| 维度 | 等比缩放 | 自适应 |
|---|---|---|
| 字号 | 随屏放大缩小（小屏偏小、大屏偏大） | 固定（各屏一致，最易读） |
| 信息密度 | 恒定——每屏内容量都差不多 | 可变——大屏一屏看到更多 |
| 平板 / 大屏 | 内容被整体放大，常显得「傻大」、浪费空间 | 可切多栏、限宽居中，真正利用空间 |
| 系统大字体（无障碍） | 易打架（已缩放，再叠加系统缩放会失控） | 天然兼容（dp 与系统字号缩放各司其职） |
| 与设计稿一致性 | 任意设备像素级等比还原 | 仅基准宽设备最贴稿，其余靠 reflow |
| 实现成本 | 低（一个 `scale()` 包住所有数字） | 中（需设计断点、flex 布局、多套排布） |
| 跨 Web | 差（Web 本就该 reflow，强行缩放别扭） | 原生契合（CSS 媒体查询就是这套） |

### 各自的适用场景

**选「等比缩放」当：**

- 纯手机 App、不上平板 / Web——设备宽度区间窄，缩放幅度小、副作用可控；
- 设计驱动、要求像素级复刻稿子——营销活动页、游戏 UI、强视觉产品；
- 画布型 / 固定比例界面——图表、海报编辑器、相机取景框这类「整体是一个视觉单元」的界面。

**选「自适应」当：**

- 跨端（Web + 移动）——Web 必须 reflow，强行缩放很怪；
- 设备跨度大（手机 ↔ 平板 ↔ 桌面）——大屏要多栏、要限宽，等比放大会「傻大」；
- 内容 / 信息密集型——社交流、电商列表、后台、设置页——用户要的是「大屏看更多」而非「看更大」；
- 重视可读性与无障碍——字号固定且尊重系统设置。

## 六、推荐：分而治之的混合方案

成熟产品很少纯用一种，而是**按层次分而治之**：

- **布局骨架**（栏数、容器宽、主次分区）→ 自适应：断点切换 + flex 流式；
- **间距 / 字号**（设计节奏）→ 固定的 design token：既不缩放也不 reflow，保证全设备视觉一致；
- **个别确实该随屏变化的视觉模块**（如全屏 Banner 高度、首屏大标题）→ 在**那一处局部**引入缩放因子。

这样既享受了自适应的跨端、可读、大屏友好，又能在少数强视觉处做到等比还原，而不必让整个应用背上全局缩放的副作用。

### 一句话决策法

> 当大屏到来时，用户想要「**看得更大**」还是「**看到更多**」？
> 想「更大」→ 倾向缩放；想「更多」→ 倾向自适应。

## 小结

- 响应式拆成三个独立轴：**像素密度**（平台兜底，别碰）、**字体无障碍缩放**（默认开启，别乱关）、**屏幕物理尺寸**（你的主战场）。
- 跨端单位是 **dp（密度无关像素）**，密度换算由平台完成；「写死数字在不同密度上不一致」是个伪命题。
- **媒体查询的本质是纯函数**「查询字符串 vs 环境状态 → 布尔」，不依赖 CSS。因此 Web 上可编译成 `@media`、原生上可用 `Dimensions` 模拟，上层逻辑零分支。
- 读断点的 hook 用「**全局 store + useSyncExternalStore + Proxy 依赖追踪**」做到精准重渲染，是可复用的通用模式。
- **自适应**改变排布、**等比缩放**改变大小；跨端 / 内容型选前者，纯手机强视觉选后者，多数产品取**分层混合**。

工具（缩放库、媒体查询库）只是手段。先想清楚你的产品在「看得更大 vs 看到更多」上的取向，再决定每一层用哪种哲学——这才是 RN 响应式的核心。
