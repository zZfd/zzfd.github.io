[设备发现](/2026/06/18/react-native-mdns-websocket-device-discovery)和[长连接通信](/2026/06/18/websocket-device-communication-deep-dive)解决的是"设备怎么找到彼此、怎么把消息可靠地发过去"。但消息发到了,只是手段;真正的目的往往是:**让局域网里的多台设备,对同一份业务数据保持一致的视图**。

这篇讲"数据同步"本身。核心结论先抛出来——**同步方案的分水岭,不是用什么传输,而是这一个问题:**

> **这份共享数据,是「多台设备都会写」,还是「一台写、其余只读」?**

答案不同,方案截然不同。下面先讲两种模型都会用到的四个通用原语,再分别展开两种模型和它们的适用场景。

## 一、四个通用同步原语

不论哪种模型,设备间同步都绕不开这四件事:

| 原语 | 作用 |
|------|------|
| **快照(Snapshot)** | 当前状态的**全量基线**,用来让新节点一次性建立起点 |
| **事件(Event)** | 状态变更的**增量流**,每条带一个**单调递增的序号(sequence/version)** |
| **拉取(Pull)** | 节点发现自己落后时,**主动向数据源补取**缺失的部分 |
| **推送 / 广播(Push/Broadcast)** | 数据源把新变更**主动发**给消费方 |

它们组合出一个**通用的"新节点上线/重连追平"流程**,两种模型都用得上:

{% highlight text %}
① 拉快照     → 删本地、按快照重建当前状态,作为基线
② 记下序号   → 记住快照对应的 sequence
③ 增量追平   → 拉取 / 接收 sequence 之后的事件，逐条应用
④ 保持在线   → 之后持续接收推送的增量事件
{% endhighlight %}

这里有个**关键机制:缺口检测(gap detection)**。每条事件带序号,节点比对"我手上的序号"和"来的事件序号":

- 相等 → 正常应用;
- 来的序号**更大**(我落后了)→ 触发**拉取**补齐中间缺的;
- 来的序号**更小**(陈旧/重复)→ 直接忽略。

> **序号是整套同步的脊梁**:它既是顺序保证,又是缺口检测的依据,还是去重的依据(重复投递的事件因序号已应用而成为 no-op)。详见[请求-响应/消息可靠性](/2026/06/18/websocket-device-communication-deep-dive)里 `seq` 的讨论——同步层的序号就是它的放大版。

到此为止,两种模型是一样的。**差别从"谁能写"开始。**

## 二、模型 A：单写者复制状态机(多写一致性)

### 何时需要

**当多台设备都会修改同一份共享数据**——比如多个终端在编辑同一批记录、对同一条记录可能同时下笔。此时光把变更"发出去"远远不够,你必须回答:**两台设备同时改同一条,谁赢?顺序怎么定?如何保证所有设备最终看到同一个结果?**

这就需要**一致性协议**,而不仅是消息广播。

### 核心机制:单写者串行化

最务实、最常见的做法是**单写者(single-writer)模型**:

1. **选定一个节点当"主"(master)**,它是唯一的写入者/串行化点。
2. **所有写操作都路由到主**——其它节点要改数据,不是各自改完互相广播,而是**把"我想改什么"发给主**。
3. **主串行执行**:逐条仲裁(能不能改)→ 提交 → **分配下一个序号** → 持久化。
4. **主广播已提交的事件**(带序号)给所有节点;落后的节点靠拉取追平。

{% highlight text %}
   写终端 A ──"想改X"──▶  主(单写者)  ──①串行仲裁 ②提交 ③+seq ④广播──▶ 所有节点
   写终端 B ──"想改X"──▶       │                                         (含 A、B 自己)
                              └─ 同一条 X 的两个请求被“排成一队”，先到先裁
{% endhighlight %}

**单写者把"分布式并发写"降维成了"主节点上的串行处理"**——这是它最大的价值:没有多点并发写,就没有最难的那部分一致性问题。

### 一致性仲裁:乐观 + 悲观双管

串行化解决了"顺序",但还要处理"基于过期数据的修改"。两种手段配合:

- **乐观并发(CAS / 版本校验)**:每条记录带一个版本(如 `version` 或上次修改时间)。提交时主比对"请求所基于的版本"和"当前版本",**不一致就拒绝**(返回冲突,让发起方拉新版本重试)。适合冲突不频繁的普通编辑。
- **悲观锁(临界区互斥)**:对"绝不能并发"的关键操作(如最终结算/扣减),先**向主申请一把锁**(带超时,持有者下线自动释放),拿到才能操作。适合冲突代价极高、必须互斥的场景。

{% highlight javascript %}
// 乐观并发：提交时校验版本（示意）
if (record.version !== request.baseVersion) {
  throw new ConflictError('另一节点已先改，请拉取新版本后重试');
}
commit(request); record.version++;
{% endhighlight %}

### 角色词汇：Paxos-inspired,但不是严格 Paxos

这类系统常借用 **Paxos 的角色词汇**:发起写的是 **Proposer**、做仲裁与提交的是 **Acceptor**、追平日志的是 **Learner**。但要**诚实地划一条线**:

> 这是**Paxos 启发(inspired)的工程化,不是严格的 Paxos 共识**。它的本质是**「单主作为 single writer 串行化 + 仲裁」**,而非多副本对等投票达成共识。所以它**没有** quorum、**没有**自动选主、**没有**经典 Paxos 处理"dueling proposers 活锁"的那套机制——因为单写者模型从一开始就回避了多提议者竞争。

把这点写清楚很重要:既能体现你懂这套词汇的来源,又不会在"你怎么处理活锁/脑裂的形式化证明"这种问题上接不住。

### 诚实的权衡:选举与故障转移

单写者模型最大的设计轴,是**"主挂了怎么办"**:

- **自动故障转移**(自动选举 + epoch/term + 切换时收集从节点 last-known state):健壮,但复杂——要处理脑裂、幽灵写、切换期一致性,接近重做半个 Raft。
- **手动接管**(人工指定新主 + 显式让位握手 + 出现"双主"等异常时人工复位):简单得多。**在"设备数量少、现场有人值守、可短暂人工介入"的封闭局域网里,手动方案完全够用**——脑裂检测出来后弹个提示让人复位,比自动和解的工程成本低一个量级。

> 这是个**场景决定的取舍**,不是"自动一定更好"。关键是**显式认清你的脑裂/故障处理是手动还是自动,并诚实标注边界**(有没有 epoch?切换是协商让位还是抢占?),而不是假装做到了自动容错。

### 适用场景

**模型 A 适合:多个对等的"可写"设备,共享一份有强业务语义的数据,且要求强一致。** 典型特征:

- 同一条记录可能被多端并发修改,**冲突必须有明确裁决**(谁先谁后、谁赢);
- 某些操作**必须互斥**(最终提交/扣减类),不能"最终一致"凑合;
- 设备都在**同一封闭局域网**、数量有限、彼此对等(都能发起写)。

**不适合**用 CRDT 那种"无主、最终一致"来硬套——因为强业务语义(如"这单只能结一次")要求的是**互斥裁决**,不是收敛合并。

## 三、模型 B：单向推送 + 连接时拉取(单写多读)

### 何时需要

**当数据只有一个"拥有者",其余设备只是展示/消费、从不回写**——比如一个源头把状态变化推给若干显示端。因为**没有多点写,就根本不存在冲突**,整套一致性协议都可以省掉。

### 核心机制

简单得多,就两件事:

1. **连接时拉取(pull-on-connect)**:消费端一连上,先拉一份**当前全量状态**(快照)建立起点。
2. **点对点推送(push)**:之后数据源把每个增量变更**推**给消费端;消费端应用即可。

{% highlight text %}
   数据源(唯一写者)
      │  ① 消费端连接 → 拉全量快照
      ├───────────────────────────▶ 展示端 1
      │  ② 之后增量变更逐条推送
      └──push──push──push─────────▶ 展示端 2
   （消费端只读，永不回写 → 无并发写 → 无冲突 → 无需仲裁）
{% endhighlight %}

注意它**仍然用到四原语**(快照 + 事件 + 拉取 + 推送),也仍然该用**序号 + 缺口检测**来抗丢包/重连追平——但**没有写串行化、没有锁、没有 CAS、没有选举**。复杂度只有模型 A 的一个零头。

### 适用场景

**模型 B 适合:一写多读、消费端不回写、只需"看到最新"的场景。** 典型特征:

- 数据**所有权单一**,消费端是只读副本;
- **不需要冲突裁决**(因为没有并发写);
- 容忍"消费端短暂落后、追平即可",对消费端的强一致要求低。

它的好处是**极简、易维护、易扩展消费端**;代价是它**只能做单向**——一旦消费端也要回写共享数据,你就被迫升级到模型 A。

## 四、选型对照与决策

| 维度 | 模型 A 单写者复制状态机 | 模型 B 单向推送 |
|------|------------------------|----------------|
| 谁能写 | **多个对等设备都能写** | **只有一个数据源写** |
| 核心难点 | 写串行化 + 冲突仲裁 + 一致性 | 基本没有 |
| 一致性手段 | 乐观 CAS + 悲观锁 + 序号守卫 | 序号去重/追平即可 |
| 角色 | Paxos-inspired(单主串行化) | 源 / 只读副本 |
| 故障/脑裂 | 必须设计(手动或自动) | 几乎无此问题 |
| 复杂度 | 高 | 低 |

**决策只看一句话:**

> **共享数据会被多个设备写 → 模型 A;只有一个源在写、其余只读 → 模型 B。** 别用 A 的重型协议去做 B 能解决的展示同步(过度设计),也别用 B 的单向推送硬扛 A 的多写一致(数据会乱)。

一个实践提醒:**两种模型常在同一个系统里并存**——核心业务数据(多端可写)用模型 A,而把这份数据投射给纯展示设备时用模型 B。识别"哪份数据是多写、哪份是单写多读",分别选型,比追求"一套机制统一所有同步"更务实。

## 五、小结

- **同步的分水岭是"谁能写",不是用什么传输。** 先回答这个问题,再选模型。
- **四原语(快照/事件/拉取/推送)+ 序号缺口检测**是两种模型的公共地基;新节点上线都走"拉快照建基线 → 记序号 → 增量追平"。
- **模型 A(多写)** = 单写者串行化 + 乐观/悲观仲裁 + 序号守卫;角色借鉴 Paxos 但**本质是单主串行化,不是严格共识**;选举/脑裂是手动还是自动,是个**场景决定的、要诚实标注的取舍**。
- **模型 B(单写多读)** = 连接拉全量 + 增量推送,无冲突无仲裁,极简;但只能单向。
- **多写选 A、单写多读选 B**,两者常在一个系统里各管一块。
