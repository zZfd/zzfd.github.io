只要团队里同时有「多端前端」和「一堆微服务」，迟早会有人提议加一层 BFF（Backend for Frontend）。提议一出，几乎必然撞上一句质疑：「这不就是个 API 网关吗？裁字段、聚合、鉴权，网关都能干，何必再加一层？」

这个质疑很难用「BFF 能做某某事」去反驳——因为你说的每一件事，对方都能回一句「网关也能配个插件做」。**这说明分界线根本不在「能不能做」上。** 本文从一个具体的扇出场景出发，把 BFF、API 网关、领域服务这三者一刀切清楚：它们各自装的是哪一类逻辑、各自跟着谁的变化而变、为什么这是三个叠在一起的层而不是三选一。

## 一个聚合首页背后的扇出

设想任意一个内容稍微丰富的首页：顶部有用户的概要信息，中间是一列实时更新的卡片（每张卡片要拼上来自不同服务的实时数据），右上角有未读消息红点，底部还有一条个性化推荐。

界面看着是「一个页面」，后端却早已按业务域拆成了一组互相独立的服务：

- 用户服务：账户概要、偏好
- 列表服务：卡片的主体数据
- 实时数据服务：每张卡片要叠加的实时数值
- 计算服务：基于前面数据派生出来的汇总指标
- 推荐服务：个性化推荐位
- 消息服务：未读数

如果让客户端自己扛，这一屏就是 **6 次请求 + 客户端把 6 份响应拼成视图 + 客户端各自处理「某个下游挂了怎么办」**。而且你有几个端，这套扇出和容错逻辑就要用几种语言、各写一遍。

BFF 的第一个价值就出现在这里：**把这 6 个下游收敛成一个 `GET /home`，扇出、编排、容错只在服务端写一次，三端共享。**

还有一条容易被忽略、却是整个模式成立前提的边界：**那几个端，加上这层 BFF，都是前端团队负责的；那 6 个服务是后端团队负责的。** 记住这条所有权边界，后面所有结论都从它长出来。

## 分界不在「能不能做」，在两个问题

面对「网关也能裁响应」的质疑，「裁剪响应」这个理由本身就撑不住——因为它描述的是**能力**，而能力从来不是分界线。网关确实能配响应转换插件裁字段。只要你给的理由是「这件事 BFF 能做」，对方永远能回「网关也能做」。

真正的分界要换两个问题来问：

> **① 那里装的是哪一类逻辑？② 那块代码跟着谁的变化而变？**

用这两个问题一刀切下去，分界线非常清晰：

> **网关不理解载荷，它只管流量；BFF 存在的全部理由，就是去理解某一个客户端、专门为它塑形载荷。**

- **API 网关**是横向的、通用的基础设施：TLS 终止、路由、限流、令牌校验、日志、CORS。它的本质特征是**不知道、也不关心响应里那串字段是什么意思**，对所有客户端一视同仁。它是被「配置」出来的（声明式插件），归属平台/基础设施团队，只在「基础设施策略」变化时才改。
- **BFF**是纵向的、绑定某个产品体验的：为这一屏该调哪几个服务、怎么把列表和实时数据 join 成一个视图模型、A 端首页要这个形状而 B 端要另一个形状、某类用户看某类内容要置灰或脱敏。它的本质特征恰恰是**必须理解载荷的含义，因为它和某一个前端的需求绑死**。它是被「编程」出来的（有测试、有发布流水线的真实服务），归属前端团队，只在「那个前端的产品需求」变化时才改。

「裁剪」之所以不够格当分界线，是因为裁字段只是塑形里**最机械的一端**，网关确实能干。BFF 真正的活是网关装不下的那些：

- **编排**——并行扇出、部分失败时按客户端策略降级；
- **跨服务组装**——把多个域的响应 join 成一个前端直接能渲染的视图模型；
- **客户端专属的展示逻辑**——脱敏、置灰、按端做 i18n；
- **有状态的协议适配**——比如某端把令牌存在服务端、某端要拿一次性凭证去换会话。

这些都不是「配一条规则」能解决的，而是**会随某一个前端一起演进的代码**。

## 三者各就各位

把上面的判断摊成一张表，三层的位置就一目了然：

| 维度 | API 网关 | BFF | 领域/后端服务 |
|---|---|---|---|
| 围绕什么组织 | 流量 | 某个客户端的体验 | 某项业务能力 |
| 知不知道载荷含义 | 不知道（也不该知道） | **必须知道** | 知道，但与客户端无关 |
| 数量 | 一个，服务所有人 | **每端一个** | 按业务域划分 |
| 归属 | 平台/基础设施团队 | **前端团队** | 后端团队 |
| 怎么造出来的 | 配置 | 编程 | 编程 |
| 拥有业务数据吗 | 否 | **否**（无事实来源） | **是**（事实来源） |
| 随谁变 | 基础设施策略 | 某前端的产品需求 | 业务规则 |

## 为什么塑形逻辑不能塞进共享网关

有人会想：那把这些客户端专属的塑形逻辑也写进网关不就行了？问题在于，网关是**所有端共享**的一层。把专属逻辑塞进一个共享层，会稳定地长出三个病：

**1. 它会变成谁都不敢动的「神级对象」。** 一个共享层服务所有端，迟早堆满 `if (client == A) { … } else if (client == B) { … }`，最后烂成一个没人拥有、人人害怕的分布式单体——而这恰恰是 BFF 当初被发明出来要逃离的困境。每端一个 BFF，每个才能保持小而内聚。

**2. 它把团队变成彼此的阻塞。** 一个组件的归属边界，应该和「会去改它的那个团队」的边界重合——这就是**康威定律**在架构上的直接应用。塑形逻辑放进共享网关，意味着 A 端团队想微调一下自己的首页形状，却要去碰 B 端、C 端、基础设施团队都依赖的同一个共享件——一次本该是「改自己页面」的产品微调，被迫升级成跨团队协调。而每端一个、归前端自己，改自己的那份不惊动任何人。**这个「自己拥有、按自己节奏发布」的能力，就是 BFF 存在的全部意义。**

**3. 能转换 ≠ 该由它转换。** 声明式插件适合的是无状态、通用、单请求内能完成的规则。一旦你的「转换」需要再去调一个服务、需要处理一次超时、需要把两个响应 join、需要按业务规则置灰——你已经长出了网关配置装不下的东西。你需要的是一个能写代码、能写测试、能灰度发布的环境。**那就是一个服务，不是一个插件。**

## BFF 和普通后端服务，以及腐化信号

最后要和「普通后端服务」划清界限，否则 BFF 很容易悄悄退化回去。

普通后端服务围绕**业务能力**组织（账户、订单、支付……），且天然**与客户端无关**——谁来调都给同一份数据，它持有事实来源（source of truth）。

BFF 正相反：它围绕**客户端/体验**组织，刻意做成**客户端专属**；它**不拥有任何业务数据、不持有任何事实来源**，是一层可丢弃、可随时重建、可水平复制的薄层。

由此得到一个非常好用的**腐化信号**：

> **如果业务规则开始往 BFF 里钻——它自己算钱、自己定校验规则、自己直连数据库存了只有它知道的状态——那它就不再是 BFF 了，正在退化成又一个普通后端服务。**

BFF 一旦开始持有「只有它知道的事实」，它和领域服务之间的边界就破了。守住「不持有事实来源」这一条，BFF 才始终是那层薄薄的、可丢弃的塑形层。

## 它们是叠层，不是二选一

回到最初的质疑——「BFF 不就是个网关吗」。现在答案清楚了：它们根本不是竞品，而是同一条请求链上、不同层各干各的活：

```
客户端
  → API 网关（通用 · 流量 · 基础设施）
  → BFF（专属 · 编排塑形 · 前端团队）
  → 领域服务（业务 · 事实来源）
```

网关在最外层管「所有进来的流量该被怎样通用地处理」；BFF 在网关之后管「这一个客户端、这一屏，到底要什么形状的数据」；领域服务在最里层管「业务事实是什么」。三层叠加，各司其职。

**一句话带走：**

- 网关管**流量**，BFF 管**某个客户端的体验**。
- 网关是**配置**出来的，BFF 是**编程**出来的。
- 网关**一个、服务所有人**；BFF **每端一个、归属那端的前端团队**——而这个归属，正是它存在的理由。
