上一篇讲 BFF 容错时，反复出现一句结论：**慢请求把「连接」钉死、占着资源不还，最终堆成资源耗尽型级联。** 但「连接」到底是什么？为什么 HTTP/1.1 下一个慢响应能独占它整整 8 秒？「连接池耗尽」和「文件描述符耗尽」是不是两回事？keep-alive 又在这中间扮演什么角色？

这篇把这条底层链路一次串清楚。理解了它，你对上层任何「连接池满了」「fd 不够了」「偶发 ECONNRESET」的故障，都会有一张统一的物理图景。

## socket = TCP 连接 = fd：同一根管子的三个剖面

第一个要打通的认知：**「socket」「TCP 连接」「连接池里的一个连接」指的是同一根物理管子**，只是站在三个不同的层，各叫一个名字。

```
HTTP 连接   ← 应用层:在这条管子上跑的「请求/响应」对话
   ↑ 跑在
TCP 连接    ← 传输层:由四元组(源IP:源端口 → 目标IP:目标端口)唯一确定的那条管子
   ↑ 操作系统给你的把手是
socket / fd ← OS 层:你在代码里拿到的句柄。Linux 上 socket 就是一个文件描述符(fd)
```

关键点：**HTTP 不是另一条连接，它是寄生在那条 TCP 连接上的对话**（HTTPS 中间还垫一层 TLS 会话，同样跑在这条 TCP 上）。所以当你在不同语境听到「socket 占满」「连接池满」「fd 耗尽」，很多时候它们说的是**同一批被钉住的 TCP 连接，在不同层面同时撞上限**。

## 为什么 HTTP/1.1 下慢请求会占住连接

HTTP/1.1 有一条铁律：

> **一条 TCP 连接，同一时刻只能跑一个请求 / 响应。响应没收完，这条连接既不能复用、也不能还回池子。**

于是当一个下游慢吞吞 8 秒才返回时，那条「调用方 → 下游」的 TCP 连接，从「请求发出」到「响应完整收到」的整整 8 秒里被这**一个**请求独占——既不能跑别的请求，也不能 keep-alive 还回池。

这就是「慢」占资源的**物理实质**：它把一条 TCP 连接钉在「已建立但用不了」的状态上 8 秒。而「挂」是连接根本没建起来（`ECONNREFUSED`），5ms 就失败释放。同样一次失败，「慢」的资源占用时间是「挂」的上千倍——这正是上一篇「慢比挂可怕」的物理根源。

## 连接池 / fd / 端口：三道墙同时撞

「连接池被占满」和「fd 被耗尽」不是两个独立故障，而是**同一批被钉住的 TCP 连接，在两个层面同时撞上限**：

- **应用 / 连接池视角**：数的是「有几条到某个下游的连接」（`maxSockets` / `connections` 这类参数）。
- **操作系统视角**：每条 TCP 连接（无论入站还是出站）都占用进程的一个 **fd**，而进程的 fd 总数有硬上限（`ulimit -n`）。

出站每多钉住一条连下游的连接，就 = 多占一个 fd，此外还吃掉一个**本机临时端口**（Linux 默认约 2.8 万个）。

入站和出站本质完全一样（都是 TCP / 都吃 fd），只是「被占住的理由」不同：

- **出站**被占：下游的响应迟迟没回来。
- **入站**被占：聚合页还没拼完，给客户端的响应发不出去，那条「客户端 → 服务」的连接也只能挂着。

所以一个慢下游，会**从出站和入站两头同时**吃掉进程的 fd 和连接配额。

## keep-alive：把握手的「路费」从每请求一次摊成每连接一次

### 没有它的世界：每个请求都重建 TCP

建一条 TCP 连接本身有昂贵开销。没有 keep-alive（HTTP/1.0 的默认），每发一个 HTTP 请求都要完整走一遍：

```
① TCP 三次握手(1 个 RTT)
② TLS 握手(HTTPS,再 1~2 个 RTT)
③ 发请求、收响应
④ TCP 四次挥手,连接关闭、销毁
   —— 下一个请求回到 ①,从头再来
```

真正传数据的第 ③ 步可能只要几毫秒，但前面的握手白白搭进去一两个 RTT。放到「一个聚合页扇出 6 个下游」的场景，每次扇出 = 6 次全新握手，延迟完全被握手成本主导。

更糟的是：海量短命连接关闭后会进入 TCP `TIME_WAIT` 状态（滞留约 2×MSL，几十秒到 1 分钟），堆积起来会**吃光临时端口**，最后连新连接都建不出来。

### 它在做的事

> **keep-alive 让一条 TCP 连接在一次请求 / 响应结束后不立即关闭，而是留着给下一个请求复用。** 握手只在第一次付一次钱，后面成百上千个请求共享这条已经建好的连接。

它也叫**持久连接**，在 HTTP/1.1 里是**默认行为**（除非显式 `Connection: close`）。

### 和连接池绑死（最容易混的一点）

很多人分不清 keep-alive 和连接池的关系，其实它俩是**同一套机制的两半**：

- **keep-alive** 负责：用完别关，留着。
- **连接池** 负责：把这些留着的连接存起来、管理、复用——下一个请求先从池里捞一条空闲的现成连接，捞不到才新建。

> **keep-alive 让连接「可复用」，连接池是那个「存放可复用连接、并把它们分配出去」的容器。没有连接池，keep-alive 几乎没有用武之地。**

回头看上一篇说的「连接池里的一个连接被慢请求占住不还」，那个「还」字，还的就是 keep-alive 的连接池。**慢请求破坏的，正是这个「用完归还、下次复用」的循环。**

### 实操：默认值是坑

```js
// 原生 http:历史默认 keepAlive: false,每个请求都在重建连接!必须显式开
import http from 'node:http';
const agent = new http.Agent({
  keepAlive: true,
  maxSockets: 100,        // 这条线路最多 100 条可复用连接(也就是池大小 / 隔离配额)
  keepAliveMsecs: 30_000, // 空闲连接每隔 30s 发 TCP keep-alive 探测包保活
});

// undici(Node 全局 fetch 的底层):默认就开 keep-alive
import { Agent } from 'undici';
const agent2 = new Agent({
  connections: 100,          // 池大小(每个 origin)
  keepAliveTimeout: 30_000,  // 一条连接空闲多久后关闭
  keepAliveMaxTimeout: 600_000,
});
```

### keepAliveTimeout 两端必须协调（经典暗坑）

连接留着复用，总得有「空闲多久没人用就关掉」的超时。坑在于：**这个超时两端各有一个。**

如果**下游服务器的空闲超时比调用方短**：下游已经悄悄关掉了连接，但调用方以为它还活着，从池里捞出来就发请求 → 撞上对方早已关闭的连接 → `ECONNRESET`，请求莫名失败。这种失败**偶发、无规律，极难排查**。

> **经验法则：让客户端（调用方）侧的空闲超时，略小于服务端侧。** 保证「要关也是我这边先主动关、然后用一条干净连接」，而不是捞到一条对方刚关掉的死连接。

（这也是不少服务框架默认 `keepAliveTimeout` 偏小、容易和上游负载均衡 / 反向代理默认 60s 打架的那类著名坑的根源。）

## RTT：一笔省不掉的固定「路费」

前面反复说「握手要付几个 RTT」，那 RTT 到底是什么：

> **RTT（Round-Trip Time，往返时延）= 一个数据包从你发出、到对端、再把回应送回来，这一个来回所花的时间。**

它量的是**来回**，因为网络通信几乎都是一来一回的对话——你能直接测到它（一个 `ping`），它也真正影响你。它主要由**物理距离 + 网络路径**决定，**和数据量基本无关**——哪怕只发 1 个字节，也得等一个完整来回。

| 场景 | RTT 量级 |
|---|---|
| 同机房内 | < 1ms |
| 同城不同机房 | 1~3ms |
| 国内跨地域 | ~30ms |
| 跨洲 | ~150~200ms |

把它接回 keep-alive 就一目了然：握手之所以贵，是因为它要额外付好几个 RTT（三次握手 1 个 + TLS 1~2 个）。假设 RTT = 30ms：

- **不用 keep-alive**：每个请求 ≈ 4 个 RTT ≈ 120ms，其中 ~90ms 全耗在握手这个「路费」上。
- **用 keep-alive**：握手只第一次付，后续每个请求 ≈ 30ms。

> **握手成本是按 RTT 计的，而 RTT 是省不掉的固定路费——所以唯一的优化方向，就是别反复付。** 这就是 keep-alive 存在的全部意义。

## HTTP/2 的差别：级联不消失，只换上限

有人会问：上了 HTTP/2 是不是就没这问题了？

HTTP/2 一条 TCP 连接能**多路复用**几十上百个并发流（stream），不再是「一请求一连接」，所以你可能**不会先以「连接池耗尽」的形式倒下**。但级联**不会消失**，只是换了个上限先撞：

- HTTP/2 每条连接有 `MAX_CONCURRENT_STREAMS` 上限（常见 ~100），撞满照样阻塞。
- 每个卡住的请求该占的内存、上下文、入站连接、待决回调，一样都没省。

> **无论 HTTP/1.1 还是 HTTP/2，「慢请求赖着共享资源不放」这个本质不变，变的只是你先用光哪一种资源。** 所以容错（超时、隔离、熔断）永远省不掉——协议升级换不来安全阀。
