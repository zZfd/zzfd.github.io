「用 Cookie 还是 JWT？」「Session 和 Token 哪个更安全？」——这类问题在网上吵了十几年，至今没有共识。但争论之所以无解，是因为问题本身就**把不在一个维度上的东西摆成了三选一**。

一旦你看清 Cookie、Session、JWT 分属**两条互相垂直的轴**，整件事会瞬间清晰：四种组合各自成立、各有适用场景，根本不存在「谁取代谁」。这篇就把这两条轴、它们的自由组合、以及随之而来的吊销 / 性能 / 安全取舍，一次讲透。

## 解锁点：它们在两条垂直的轴上

混淆的根源，是把这三个词摆成「三选一」。错。它们分属两条**互相垂直**的轴：

- **Cookie 是「运输方式」**——它只回答一个问题：「凭证怎么在浏览器和服务器之间携带」。本质是一个 HTTP 头机制：服务器用 `Set-Cookie` 下发，浏览器之后在每个请求里**自动**带上。它**根本不关心**你往里面装的是什么。
- **Session vs JWT 是「策略」**——它们回答的是「凭证里装什么、关于你的真相存在哪」：
  - **Session（有状态）**：凭证是一串**无意义的随机 id**，关于你的真相全部存在**服务端存储**里。
  - **JWT（无状态）**：凭证**自带身份信息**，用签名防篡改，真相**写在 token 自己身上**，服务端不查库就能验证。

**两条轴垂直，可以自由组合**，四个格子全都成立：

| 运输 \ 策略 | Session（真相在服务端） | JWT（真相在 token 自身） |
|---|---|---|
| **Cookie**（浏览器自动带） | 传统会话（Web 端最常见默认） | cookie 里装一个 JWT |
| **Bearer**（客户端手动带） | header 里带 session id | 经典 Bearer JWT（`Authorization: Bearer …`） |

看清这张表，「Cookie vs JWT」就是个伪命题——它们一个是纵轴、一个是横轴，可以同时出现在一个格子里。

## 走一遍：Cookie × Session 的完整生命周期

以最经典的「Cookie × Session」组合为例，走完登录到登出的全程，把有状态会话的每个环节看清楚。

**① 登录（签发会话）。** 验证凭证（查用户表、比对密码哈希）→ 通过后在**服务端的 session 表里建一条记录**（含 session token、userId、过期时间）→ 用 `Set-Cookie` 把 **session token** 下发给浏览器。注意：cookie 里装的**不是**用户信息，只是一把指向 session 行的「无意义钥匙」。

cookie 的安全属性要配齐：

- `httpOnly`——让前端 JS 读不到它，防 XSS 窃取；
- `Secure`——强制只在 HTTPS 上传输；
- `SameSite=Lax`（或更严）——缓解 CSRF。

合起来就是：**真相（身份）留在服务端，浏览器只攥着一把读不出内容的 httpOnly 钥匙。** 这是 Web 端会话安全的基本盘。

**② 后续请求（校验）。** 浏览器自动带上 cookie → 服务端取出 session token → **查 session 表** → 存在且未过期 → 放行，加载用户。

**③ 滑动过期。** 会话设一个绝对过期（比如 7 天）；每次使用若距上次刷新超过某个阈值（比如 1 天），就把过期时间顺延。这样**活跃用户不会被平白踢掉，长期不用的会自然失效**。

**④ 登出 / 吊销（这是 session 的看家本领）。** 真相在服务端那张表里，所以**登出 = 删掉那条 session 行**；下一个请求一查「没这条了」，**当场失效**。挂失、远程下线、强制所有设备登出，全靠它。

> 这就是那句「session 的吊销是免费的」——因为它**每次本来就要查库**，吊销只是让那次查询查不到而已，没有任何额外成本。

## cookie cache：「性能 ↔ 即时吊销」的一个旋钮

上面的流程有个性能软肋：**每个请求都查一次 DB**。高 QPS 下这是实打实的负担。

通用的优化手法是给会话加一层 **cookie 缓存**：把会话的有效性信息**签名后直接编码进 cookie 本身**，服务端从 cookie 验签即可确认会话有效，**不必每次查库**；再给这个缓存设一个较短的 `maxAge`，保证数据定期刷新。（顺便，这正好落在前面矩阵里「Cookie 里装 JWT」那个格子——一个临时的、自包含的签名令牌，贴在 session 之上当性能缓存。）

但它有代价：**被吊销的会话，在其它设备上可能仍然有效，直到那台设备的 cookie 缓存按 `maxAge` 自然过期为止**——因为缓存数据存在客户端，服务端没法直接伸手删掉其它设备上的 cookie。

于是「性能 vs 即时吊销」这个看似二选一的矛盾，被做成了**一个可调的旋钮**：

- **纯 session（不开 cache）** = 每请求查库、**可即时吊销**，但慢。
- **开 cookie cache** = 不查库、**快**，但吊销有最多 `maxAge` 的延迟。

挂失、风控这类强即时场景，就把 `maxAge` 调小甚至关掉缓存；普通场景就放宽换性能。**没有哪个绝对正确，重点是认识到它是一个你能拧的旋钮。**

## 往无状态推到底：纯 JWT 与「补回吊销」

把策略轴推到极致，就是**纯无状态**：会话数据全部存在签名 / 加密的凭证里，服务端**从不查库，只验签 + 验过期**。这就是纯 JWT 的全部取舍兑现——**快，但难以即时吊销**（token 一旦签发，在过期前服务端无法单方面让它失效）。

如果既要无状态的性能、又要能即时吊销，通用手法是**给验签挂一道 O(1) 的吊销检查**，而不是退回完整 session：

- **token 黑名单**：把要作废的 `jti` 写进 Redis，TTL = token 的剩余寿命；
- 或更适合「一键全端下线」的**用户级失效时间戳**：记一个 `revokeBefore:{userId}` 时刻，凡签发时间早于它的 token 全部作废。

每个请求只需问一个布尔问题（「在不在黑名单 / 是不是早于失效点」），绝大多数答案是「否」直接放行，远比「查一条完整 session」轻。**这是无状态认证补回即时吊销的标准做法。**

> 还有一个容易混的点：会话凭证里的 JWT，和**服务间身份令牌**的 JWT，是两码事。前者是「用户登录态」，后者是「BFF / 微服务之间证明身份」。同样是 JWT，用途和生命周期完全不同，别混为一谈。

## 三端差异：本质是「浏览器 vs 非浏览器」

为什么 Web、App、小程序的认证方案常常不一样？答案全在矩阵的**纵轴（运输）**上：

- **Web**：浏览器能自动带 cookie、能存 httpOnly cookie → **Cookie × Session 是绝配**，安全性和便利性天然契合。
- **App / 小程序**：**没有「浏览器自动带 cookie」这套机制**，httpOnly 也无从谈起 → 只能走 **Bearer**：把凭证放进 `Authorization` header 里手动携带（里面装 session token 还是 JWT 都行——这又回到了策略轴的自由组合）。

> 网上吵的「Cookie 派 vs Token 派」，根子根本不是「哪个更安全」，而是 **「你的客户端是不是浏览器」**：浏览器有 cookie 自动携带 + httpOnly 的便利就用 cookie；非浏览器没有这套机制，就只能手动带 token。

## Cookie 模式特有的坑：CSRF（以及它的镜像 XSS）

Cookie 的「自动携带」是便利，但**正是这个「自动」带来了 token 模式没有的 CSRF**：恶意站点能诱导你的浏览器**自动带上**你的 cookie 去发请求，而你毫不知情。所以 cookie 模式必须额外防 CSRF，常见三道防线：

1. `SameSite=Lax/Strict`——限制跨站请求自动带 cookie；
2. 校验 `Origin` / `Referer` 头是否来自可信源；
3. 用 Fetch Metadata 头（`Sec-Fetch-Site` 等）对敏感操作做额外校验。

而 **Bearer token 因为是手动带、不会被浏览器自动附加，天然不吃 CSRF**——这是 token 模式的真实优势。但它的代价是：token 通常存在 JS 能碰到的地方（localStorage 等），于是又得防 **XSS**。

> **两条运输方式各有各的攻击面：Cookie 防 CSRF（但 httpOnly 帮它挡住了 XSS 窃取），Bearer 免 CSRF（但要自己防 XSS）。没有银弹，只有「你更能守住哪一边」。**

## 一句话锁死

> **Cookie 是「怎么带」（运输），Session / JWT 是「装什么、真相在哪」（策略），两条轴垂直、自由组合。有状态会话把真相放服务端，删一行即时吊销；cookie cache 在「查库的即时性」和「不查库的性能」之间给你一个 `maxAge` 旋钮；往无状态推到底就是纯 JWT 的取舍，用 O(1) 黑名单 / 失效时间戳补回吊销；而三端差异的本质，不过是纵轴上「浏览器能自动带 httpOnly cookie、非浏览器只能手动带 bearer token」。**
