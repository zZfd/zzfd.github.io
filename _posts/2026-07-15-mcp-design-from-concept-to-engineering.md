写这篇之前，我一直用一句话来锚定 MCP（Model Context Protocol，模型上下文协议）到底和传统 API 差在哪：

> **API 是给「确定的代码」调用的；MCP 是给「会推理的 AI 模型」调用的。**

交互对象从「按预设流程走的代码」变成了「根据意图自主决策的模型」，几乎所有设计范式都随之改变。这篇是一份尽量完整的 MCP 参考：从概念、三大核心要素、与 API 的区别，到它和 Agent / LLM / 宿主应用的关系、设计原则、认证鉴权体系、与 CLI 的取舍、分页实现，最后用「本地 CLI 把企业 API 封装成 Agent 能力」这个真实模式做一次架构剖析。它的底层消息格式是 JSON-RPC 2.0，那部分我单独写成了 [JSON-RPC 2.0 协议详解](https://zzfd.github.io/2026/07/15/json-rpc-2.0-protocol-explained)，本文不再展开。

## 一、MCP 是什么：给「会推理的模型」用的接口层

传统 API 的接收方是程序员写死的代码，调用序列在编码期就确定了。MCP 的接收方是大语言模型——它在运行时根据用户意图，**自主决定要不要调、调哪个、按什么顺序调**。这一点决定了 MCP 不是又一种 REST，而是一层「语义包装」：把晦涩的数据接口，翻译成模型能读懂、能灵活运用的**上下文**和**工具**。

它仍然是经典的 CS 架构，但角色要分清楚：

- **Host / Client（宿主 / 客户端）**：像 Claude Desktop、Claude Code、Cursor、Zed 这类应用，或你自研的 AI 产品。它是真正的调度中枢。
- **Server（服务端）**：你写的那段程序，对外暴露能力（工具 / 资源 / 提示词）。
- **LLM（大模型）**：提供推理能力，但**它本身完全不懂 MCP 协议**。

很多人会画成 `LLM → Client → Server`，方向就错了。更准确的流转是这样一个闭环：

```
用户 ⇄ MCP Client ⇄ LLM（云端大模型）
             ⇅
        MCP Server（你的代码）
```

一次完整调用的链路：

1. Client 从 Server 拉取能力清单（工具的 Schema）。
2. Client 把这些能力**翻译**成 LLM 认识的「函数调用（Function Calling）」格式，连同用户的问题一起发给 LLM。
3. LLM 推理后告诉 Client：「去调用工具 A，参数是……」——**说完这句它就停机了**。
4. Client 领命，向 Server 发起真正的调用。
5. Client 拿到 Server 的结果，再塞回给 LLM 继续推理。

看清这条链路，你会发现 Client 的核心职责就两个字：**翻译**和**跑腿**。LLM 只负责「想」，真正的执行、循环、状态，都在 Client（以及它所属的 Agent 框架）手里。

## 二、三大核心要素：Resources、Tools、Prompts

规范里，MCP 把 Server 能暴露的能力明确分成三类。虽然现实中大家 90% 的精力都花在 Tools 上，但把三者的边界讲清楚，才能理解这套设计的完整意图。

**Resources（资源）——AI 的「只读知识库」。** 供模型读取的上下文数据，像挂载给 AI 的一个只读文件系统。特征是：**只读**（模型只能看不能改）、**URI 寻址**（用类似 `file://`、`db://` 的路径标识）、**可订阅**（数据变化时 Server 主动推送更新通知）。典型场景：代码仓库目录、一份接口文档、一段日志。

**Tools（工具）——AI 的「机械臂」。** 供模型调用的执行函数，赋予 AI 改变外部世界、或动态获取特定数据的能力。特征是：**读写皆可、以动作为主**（可以是发邮件、删文件这类破坏性操作，也可以是带参数的动态查询），**由模型在对话中主动决定是否调用**。典型场景：`send_email`、`search_web`、`query_by_condition`。

**Prompts（提示词）——AI 的「剧本与工作流」。** 可复用的、结构化的指令模板，带占位符参数。特征是：**通常由用户在前端主动触发**（在客户端点一个按钮 / 敲一个斜杠命令），用来快速开启一段有特定目标的对话。它返回的往往不是一段纯文本，而是一组标准的对话消息，用于瞬间给模型建立起特定的角色和上下文。

三者怎么协作？用**做菜**来类比最直观，把 LLM 想成一位厨师：

- **Prompts（剧本）**＝顾客点的菜谱要求：「做一道低脂宫保鸡丁，不放花生。」它设定了这顿饭的目标和规则。
- **Resources（资源）**＝厨房里敞开的冰箱和储物柜：厨师随时转身能看到有哪些现成食材（文档、文件），是静态、一眼可见的上下文。
- **Tools（工具）**＝厨师手里的刀、灶，甚至外卖电话：冰箱没肉了就打电话订（`order_grocery`），要改变食材状态就动刀（`chop_meat`）——**动态地获取或改变世界**。

完整交互流：**用户触发一个 Prompt → AI 带着目标启动 → 查阅现有 Resources 了解背景 → 发现还缺信息或要执行操作，于是调用 Tools → 完成任务返回。**

### 为什么现实中我们几乎只关注 Tools？

这不是偷懒，而是有硬道理：

1. **Tools 对 Resources 向下兼容。** 技术上，任何 Resource 都能包装成一个 Tool——写个 `read_file(path)` 就能替代资源读取。既然一个 Tool 读写通吃，开发者往往懒得再单独实现一套 Resource 的 URI 路由。
2. **大模型的核心进化恰好是 Function Calling。** 头部厂商这些年微调的主方向就是让模型极其擅长判断「该用哪个工具、参数怎么填」。Tools 完美契合这一技术范式。
3. **AI 的价值在于「能动性（Agentic）」。** 只给资源，AI 顶多是个更聪明的搜索引擎；只有给了 Tools，它才能真正替你干活。大家追求的正是这种「让 AI 动手」的震撼。
4. **Prompts 常被硬编码在客户端。** 很多开发者不把 Prompts 作为协议的一部分暴露，而是直接写死在应用前端（系统提示、规则文件），于是 Server 端的 Prompts 显得多余。

一句话收束：**Resources 提供静态上下文，Prompts 定义任务目标，Tools 提供执行能力。** Tools 最灵活、最具拓展性，也最顺应当前大模型的技术趋势，所以独占 C 位。

## 三、MCP 与 API：不是取代，而是语义包装

两者最大的区别在于**交互对象**，它像多米诺骨牌一样推倒了后面所有设计选择：

| 维度 | 传统 API（REST / GraphQL） | MCP |
|---|---|---|
| 服务对象 | 程序员、固定的代码逻辑 | 大语言模型、AI Agent |
| 核心要素 | 路由、请求方法、数据载荷 | 资源、工具、提示词模板 |
| 描述方式 | 侧重结构准确性，给开发者看 | 侧重语义化描述，让 AI 能「读懂」 |
| 执行逻辑 | 强确定性：严格按预设流程调用 | 弱确定性：AI 自主决定是否调、按什么顺序调 |
| 容错机制 | 返回状态码与错误堆栈，代码捕获 | 返回自然语言错误提示，引导 AI 自我纠错 |

但**它们不是替代关系**。MCP 是建立在 API 之上的一层包装，三点联系很实在：

1. **底层依赖**：MCP Server 内部往往就是去调已有的传统 API 来取数、执行操作；它的传输本身也跑在进程管道或 HTTP 之上。
2. **规范契约**：两者都需要严格的输入输出 Schema（都用 JSON Schema 定义参数）。
3. **安全机制**：都要考虑鉴权、访问控制和限流。

所以 MCP 更像一个尽职的**翻译官**：把给开发者看的、结构精确但语义贫瘠的 API，翻译成 AI 能理解并灵活运用的上下文和工具。

## 四、MCP 与 Agent、LLM、宿主应用的关系

这里有个常见误解要先澄清：**规划能力到底是谁的？**

准确的说法是：**规划的「智力」来自 LLM，执行规划的「闭环」由 Agent 框架赋予。** LLM 像一个被绑在椅子上的绝顶聪明的大脑——你问它「怎么把大象装冰箱」，它能完美规划出第一步第二步第三步，但它只能把步骤打印成文字，自己动不了。它的本质是一个**无状态函数**：输入一段文本，预测下一段文本。

Agent 框架（LangChain、AutoGen，或者你自己写的一个 `while` 循环）为这个大脑配上「操作系统和躯干」，建立一个执行循环（ReAct Loop）：

1. Agent 把问题丢给 LLM：「你想怎么做？」
2. LLM 规划：「我需要先调用 `search_weather` 查北京天气。」——**输出这句后 LLM 停机**。
3. Agent 截获这条指令，代替 LLM 真实调用天气接口，拿到「25 度」。
4. Agent 把「25 度」塞回 LLM：「结果拿到了，下一步？」
5. LLM 接着规划……如此循环。

所以：**智力属于 LLM，流程控制（循环、调用工具、记忆状态、错误重试）属于 Agent。** 而 **MCP Client 是 Agent 的「骨架」和「感官」**——它赋予 Agent「行动能力」，统一接入外部世界的各种 Server，省掉为每个新工具手写对接代码的活。很多现代框架里，你实例化一个 Agent 时，底层其实就是启动了一个 MCP Client 模块。

至于 Prompts / Resources / Tools 的**消费方**，全是 MCP Client。它们在 Client 内部的用法各不相同：

- **Tools**：Client 转成 LLM 的函数 Schema 发给模型；模型决定调用时，Client 再去请求 Server 执行。
- **Resources**：触发读取时，Client 从 Server 拉取内容，作为**文本上下文拼进发给 LLM 的 Prompt**。LLM 根本不知道「资源」这个概念，它只看到一大段被喂进来的背景资料。
- **Prompts**：Client 从 Server 取模板，通常在 UI 上渲染成快捷按钮或斜杠命令；用户点选并填参后，Client 渲染出完整提示词发给 LLM。

### 什么时候需要自己造 MCP Client？

日常场景下，你只需要写 Server，注册到现成的宿主应用里就能用——它们就是你的 Client。真正需要自研 Client 的，通常是这四种情况：

1. **把 AI 嵌进自己的产品**：做一个内部智能客服或知识库问答机器人，你不可能让业务人员去装一个通用桌面客户端，得自己写前端 / 后端，它同时连大模型和各业务 Server。
2. **要对接非官方绑定的模型**：官方客户端往往深绑自家模型；想用别的云端模型或本地部署的模型来驱动你的 Server，就得用支持这些模型的 Client 框架自己搭。
3. **要定制交互（Human-in-the-loop）**：高危操作需要特定样式的二次确认弹窗，标准客户端给不了。
4. **无人值守的后台批处理**：写个脚本每天自动读邮件、总结、入库，全程无人参与聊天——你需要一个代码驱动的 Client。

## 五、设计原则：不能照搬 REST 的思维

这是全文最该反复读的一节。让一个「会推理但也会幻觉」的模型稳定地用好你的 Server，靠的是下面五条。

**1. 极其详尽的语义化描述。** 这是 MCP 设计中最重要的一环。API 的接口名只要开发者能看懂就行，但工具名和参数描述必须像写给实习生的说明书一样清楚：

- **避免缩写**：不要叫 `get_usr_doc`，叫 `search_user_documents`。
- **写清使用场景**：在描述里直接告诉 AI 什么时候用、什么时候别用。比如「用于检索用户历史订单。当用户询问物流状态时，先调此工具获取运单号。」
- **参数注释**：每个参数给一句自然语言说明，包括格式要求（如「必须是 ISO 8601 格式的日期字符串」）。

模型看不到你的实现，它对工具的全部理解**只来自这段描述**。描述写得糊，模型就猜；模型一猜，就是幻觉的温床。

**2. 恰当的工具粒度。** 模型的规划能力有限，粒度是一门平衡艺术：

- **太细碎**：一个任务要 AI 连续调 5 个原子接口，中间任何一步都可能出错或幻觉。
- **太臃肿**：一个工具挂几十个可选参数，AI 容易填错或不知所措。
- **推荐做法——提供「宏工具」**：如果一段业务逻辑通常是固定顺序（如 建档 → 计费 → 通知），就在 Server 内部封装成一个 `create_and_notify_order`，而不是让 AI 自己去协调三步。**把编排的确定性收回到代码里，只把决策点暴露给模型。**

**3. AI 友好的错误处理。** 传统 API 的报错是给代码看的冷冰冰的 `{"error": "invalid_id"}`；但 MCP 的错误信息是**返回给模型的提示词**。所以要给出行动建议：

> 不要只说「找不到该文件」。要说：「找不到该文件。请检查文件名拼写，或先调用 `list_directory` 查看当前目录下的可用文件。」

这样模型会自动进行下一步尝试，而不是直接向用户报错卡死。**把错误当成对模型的引导，而不是终点。**

**4. 严格管理上下文窗口（Token 经济）。** LLM 的上下文有限，且内容越长，注意力越涣散、成本越高：

- **绝不直接倾泻数据**：一个接口返回 1000 条记录，绝不能原样丢给 AI。
- **在 Server 端内置过滤与截断**：实现分页、关键字搜索、摘要提取，只返回最核心的 Top N。（分页怎么做见第九节。）

**5. 读写分离与安全边界（Human-in-the-loop）。** 给 AI 动手能力，也带来了误删库、发错邮件这类风险：

- **隔离操作类型**：明确区分只读的 Resources 和具有破坏性的 Tools。
- **设防线**：对转账、写库、删除、外发这类不可逆操作，设计上应**强制要求 Client 弹窗，让人类点击确认后才真正执行**。无论 Server 端把权限校验做得多严，模型本身都可能因幻觉发出错误指令（把 `delete_tmp_file` 规划成 `drop_database`），这道人类确认防线不能省。

## 六、如何定义与实现（示意）

工程上，主流生态里三者的定义都非常优雅——本质就是写普通函数，加不同的装饰器。下面是**示意**代码，重点看结构，不拘语言与具体框架：

```python
# 示意：一个 MCP Server 的三类能力定义

@mcp.tool()
def get_user_profile(user_id: int) -> str:
    """
    根据用户 ID 查询用户详细信息。
    当用户问到某人的职位、部门或联系方式时，调用此工具。
    """
    # 这里是真实业务逻辑，比如查库
    ...

@mcp.resource("system://logs/{date}")
def get_system_logs(date: str) -> str:
    """读取指定日期的系统日志内容。"""
    # 通常用于大段的、不需复杂计算的静态 / 半静态上下文
    ...

@mcp.prompt()
def code_review_prompt(language: str, code_snippet: str) -> list:
    """发起一次结构化的代码审查。"""
    # 返回的是标准对话消息，用来瞬间给模型建立角色与上下文
    ...
```

几个实现要点值得记住：

- **函数名就是工具名**，要语义清晰。
- **Docstring（函数注释）极其重要**——它就是给 LLM 看的说明书，对应第五节的第 1 条原则。
- **类型标注是必须的**，框架靠它自动生成严格的参数校验 Schema（JSON Schema）传给模型。
- Resource 用 **URI 模板**暴露，适合大段静态内容；Prompt 返回**对话消息**而非纯文本。

## 七、传输层：本地用 STDIO，远程在演进

MCP 官方支持两类底层传输，别再以为它用 WebSocket——标准生态里根本没把 WebSocket 作为传输层。

**本地场景：STDIO（标准输入输出）。** 这是最常见、最核心的用法。宿主应用在本地直接**启动一个子进程**（跑一个脚本命令），双方通过操作系统的标准输入 / 输出，以 JSON-RPC 格式通信。优势是：零网络开销、极其安全（数据根本不出本机）、配置极简。

**远程场景：从 HTTP+SSE 到 Streamable HTTP。** 当 Server 部署在云端供多方调用时走 HTTP。这一层规范一直在演进，值得如实交代：

- **早期**采用「HTTP+SSE」双端点模式：客户端→服务端走 HTTP POST（调用工具 / 读资源），服务端→客户端单独建一条 **SSE（Server-Sent Events）** 长连接用于主动推送（订阅更新、长任务进度）。
- **现在**规范推荐 **Streamable HTTP**：收敛为单端点，普通请求走一次性 HTTP 响应，需要流式或服务端推送时再按需升级为 SSE 流。它对反向代理、负载均衡、Serverless 网关和企业防火墙更友好，也简化了长连接的运维。

为什么这条线始终没选 WebSocket？因为 WebSocket 虽是全双工，但在企业级网络里常遇到反向代理断流、负载均衡不兼容、防火墙拦截；而基于 HTTP 的方案本质就是普通 HTTP 请求，对云原生基础设施极其友好，实现成本也低得多。

> 无论传输怎么变，承载在上面的**消息永远是 JSON-RPC 2.0**。STDIO 那种「请求响应乱序混在一条字节流里」的场景，正是 JSON-RPC 用 `id` 配对建立秩序的用武之地——细节见 [JSON-RPC 2.0 协议详解](https://zzfd.github.io/2026/07/15/json-rpc-2.0-protocol-explained)。

## 八、认证鉴权体系

鉴权的实现方式**高度依赖你选的传输层**。分本地和远程两条线来看。

### 本地传输（STDIO）：隐式鉴权

本地跑的时候，网络层的鉴权根本不存在，鉴权被下放给了操作系统和环境：

- **操作系统级权限**：Client 以当前系统用户的身份启动 Server 子进程，Server 只能读该用户有权访问的文件、执行的命令。个人桌面工具、本地开发天然受此约束。
- **环境变量凭证**：Server 启动时读系统环境变量（如某个第三方服务的 Token）来获取对下游的访问权限。

宿主应用**如何注入这个 Token**？它不通过什么特殊协议消息，而是在配置文件里声明一个 `env` 块：

```json
{
  "mcpServers": {
    "my-server": {
      "command": "node",
      "args": ["server.js"],
      "env": { "SERVICE_API_KEY": "***" }
    }
  }
}
```

启动子进程时，这些键值对被作为**子进程的系统环境变量**注入。Server 代码只需像普通脚本一样 `os.environ.get(...)` / `process.env.xxx` 读取即可，**不需要任何 MCP 协议层的特殊处理**。

> 一条安全红线：**绝不要把密钥写进 `args` 数组**。命令行参数在系统进程列表（`ps aux`）里是公开可见的，密钥必须严格放在 `env` 里。

### 远程传输（HTTP）：显式鉴权

Server 部署到云端、供多用户 / 多 Client 调用时，必须在 HTTP 层做严格鉴权。Token 不再靠环境变量注入，而是**附在 HTTP 请求头**里发过来，Server 在网关层 / 中间件拦截校验。三种方式对应不同信任级别：

| 方式 | 机制 | 适用场景 |
|---|---|---|
| **API Key / 静态 Bearer** | 请求头带 `Authorization: Bearer <token>`，网关校验合法性 | 企业内部基础设施、Server-to-Server 集成，信任级别高、无需用户级隔离 |
| **OAuth 2.x / 动态 JWT** | 客户端先引导用户登录拿到代表真实用户的 JWT，Server 解析出用户身份，只返回该用户有权看的数据 | 多租户 SaaS、需要细粒度用户级数据隔离，是构建面向用户 / 企业级 MCP 的标配 |
| **mTLS（双向 TLS）** | 建连时双方互验数字证书 | 零信任网络 / 金融级极高安全场景 |

**补充一个规范演进**：MCP 较新的规范已经为 HTTP 传输定义了一套基于 **OAuth 2.1** 的授权框架（授权服务器元数据发现、动态客户端注册、PKCE 等），把「远程鉴权」从各家自定义拉向了标准化。但现实里，大量部署仍在用静态 Bearer / API Key——所以下面这套「静态凭证的过期难题」在很长时间内依然是日常。

### Token 生命周期：静态凭证的现实与自动刷新

日常配置里，我们通常只往 `env` 里塞一个长期 Token（比如有效期 30 天的个人访问令牌）。它是**静态凭证**，不支持自动刷新——到期就失效。此时的真实链路很「原始」：

1. AI 调用你的工具 → 2. Server 拿过期 Token 请求上游，被返回 401 → 3. Server 捕获错误，作为一段文本返回给模型（`"Error: API Key expired, please check credentials."`）→ 4. 模型在聊天框告诉用户「你的密钥过期了」→ 5. **你手动去第三方平台重新生成密钥、改配置、重启客户端**。

由此引出一个关键澄清：**要不要在 MCP 里定义一个 `refresh_token` 的 Tool？绝对不要。** Tool 是给模型用的业务动作。把刷新 Token 做成 Tool，等于指望模型在遇到权限错误时聪明地去调它——身份认证是**基础设施层的责任，不该暴露给模型当业务逻辑**。

那真需要「自动刷新」时怎么办？分清是谁在刷新谁的 Token：

- **场景一：Server 刷新第三方 API 的 Token（最常见）。** 你的 Server 桥接了用 OAuth 的外部系统（Access Token 只有 1 小时有效期）。**逻辑全部封装在 Server 内部**：写一个带「拦截 401 → 静默刷新 → 重试」的请求包装器，对模型完全透明。模型只会觉得这次调用慢了一秒，浑然不知后台换了次令牌。这是**首选、最优雅**的做法。

- **场景二：Client 刷新访问 Server 自己的 Token。** 只有在你自研 Client 时才涉及。难点在于拦截底层网络请求：给 SDK 替换一个带刷新逻辑的 `fetch`，POST 请求收到 401 就刷新重放。还有个坑——**SSE 是长连接**，如果连接本身因 Token 过期被服务端切断，普通的请求拦截器捕获不到，必须监听传输层的关闭事件，在重连前先刷新 Token。

- **通用客户端不支持内置刷新，怎么绕？** 现状是主流通用客户端**不内置 Refresh Token 逻辑**（协议早期没规定统一的刷新端点、参数、重试策略，通用宿主无从实现一套兼容全网后端的机制）。既然不想重写 Client，脏活就得由你的 Server 或一个中间层扛：
  1. **Server 自管 OAuth 状态**（推荐）：让 Client 与 Server 之间用一个长期有效的信任（本地环境变量 / 长期内部 Key），Server 在后端自己维护刷新逻辑，对前端永远「是通的」。
  2. **本地代理网关**：写个轻量本地脚本作反向代理，`Client → 本地代理 → 云端 Server`。代理在内存里维护 Refresh Token，拦截 401 自动刷新重试，Client 全程无感。
  3. **服务端强制重定向授权**：连 Refresh Token 都失效、必须人类重新登录时，Server 在工具返回结果里放一段带登录链接的文本并标记 `isError`，模型看到就会提示用户去点链接——这是 Human-in-the-loop 的变通解法。

**一句话选型**：本地自用 → STDIO + 环境变量，不用写鉴权；公司内部公用工具 → HTTP + API Key；商业化 SaaS → HTTP + OAuth 解析 JWT，做用户级隔离。而**鉴权与状态管理的复杂性，永远封装在后端（Server 或本地代理），对前端保持接口和体验的纯净。**

## 九、分页实现逻辑：游标驱动

第五节说了「绝不倾泻数据」，分页就是最主要的抓手。MCP 规范强制采用**基于游标（Cursor-based）**的分页，而不是传统的「页码 + 每页条数」。这是为了处理流式数据和外部接口集成时，避免因数据动态增删导致的**跳过或重复**。

核心交互机制只有两点：

- **客户端请求**：想要下一页，就在参数里带上上一页返回的 `cursor`（第一页请求时没有此字段）。
- **服务端响应**：返回当前页数据，并附一个 `nextCursor`。**没有更多数据时，直接省略 `nextCursor` 字段**，客户端以此判断结束。

官方有四个内置列表操作原生支持分页：`resources/list`、`resources/templates/list`、`prompts/list`、`tools/list`。请求 / 响应长这样：

```json
// 请求（客户端发来）
{ "jsonrpc": "2.0", "method": "resources/list",
  "params": { "cursor": "eyJwYWdlIjogMn0=" }, "id": 1 }

// 响应（服务端构造）
{ "jsonrpc": "2.0",
  "result": { "resources": [ "...数据..." ],
              "nextCursor": "eyJwYWdlIjogM30=" }, "id": 1 }
```

如果你的**自定义工具**要查海量业务数据，也应套用同一套游标逻辑。服务端要做的，是把「页码 / 最后一条记录 ID」这类内部状态**编码成一个不透明字符串**：

```python
# 示意：自定义工具里的游标分页
def get_logs(query: str, cursor: str = None):
    current_page = 1
    if cursor:
        try:
            state = json.loads(base64.b64decode(cursor))
            current_page = state.get("page", 1)
        except Exception:
            # 规范要求：无效游标必须抛 -32602 Invalid params
            raise ValueError("Invalid cursor")

    page_size = 50  # 页大小由服务端绝对控制，客户端不能指定
    results, has_more = fetch_from_db(query, current_page, page_size)

    next_cursor = None
    if has_more:
        next_cursor = base64.b64encode(
            json.dumps({"page": current_page + 1}).encode()).decode()

    return { "logs": results, "nextCursor": next_cursor }
```

四条避坑要点：

- **游标必须「不透明」**：哪怕底层就是页码，也要序列化 + Base64 编码，不要直接返回 `"2"`。这防止模型擅自推测和伪造游标。
- **页大小由服务端掌控**：规范里分页请求不支持客户端指定 `pageSize`，返回多少条完全由服务端按性能和 Token 上限决定。
- **严格处理错误**：收到解析失败 / 过期 / 非法的 `cursor`，必须抛 `-32602`（Invalid params），**而不是静默返回第一页**。
- **省略即结束**：查到最后一页就不要包含 `nextCursor` 这个 key。

## 十、MCP vs CLI：Agent 的「手脚」还是「标准接口」

一个越来越流行的观察：在构建代码 / 系统级 Agent 时，直接给它一个交互式 **CLI（Shell）**，往往比为每个操作精心写 MCP Tool 更高效。原因有五个：

1. **大模型是 Bash 的「母语者」**。预训练读了海量开源代码和运维日志，模型对 `git diff`、`grep`、包管理命令的输出格式有极深的内置理解，你不用费劲把信息格式化成 JSON，它看原始终端字符串就能精准提取；让它写一行 Shell，比让它填一个它没见过的自定义 Tool Schema 更容易、幻觉率更低。
2. **极致的组合性（Unix 哲学）**。「查所有含 error 的日志，取第二列 IP，去重统计」——用 MCP 要 `list → 思考 → read → 思考 → extract` 多次往返，既费 Token 又累积出错概率；用 CLI 一条 `cat logs/* | grep error | awk '{print $2}' | sort | uniq -c` 就在本地瞬间算完，只把少量结果返回模型。
3. **零适配成本**。世界上已有数百万现成 CLI 工具；给 Agent 一个 Shell，它立刻拥有操作文件、Git、容器、云资源的能力，你不必为 `git commit` 专门写个 Tool。
4. **极省上下文窗口**。把一切都拆成 Tools，System Prompt 会挤满几十个 Schema；用 CLI 只需注入一个 `execute_bash(command)`，相当于递给 Agent 一把万能瑞士军刀，极大释放上下文空间。
5. **状态保留**。终端天然是有状态环境：`cd src` 后续命令都在该目录，`export` 后的变量后续脚本能用——这种连续性在无状态的 JSON-RPC 里模拟起来很痛苦。

但这不代表 MCP 没意义。CLI 的优势集中在**研发与运维**场景；换到企业业务集成，CLI 会遭遇灾难，而这正是 MCP 的主场：

| 维度 | CLI / Shell | MCP Server |
|---|---|---|
| 最佳场景 | 写代码、系统管理、文件处理、开发者工具 | 业务系统集成、只读知识库、严格的企业数据流 |
| 输出格式 | 非结构化文本（可能极长，Token 爆炸） | 严格结构化 JSON，易于截断和分页 |
| 安全性 | 极高风险（`rm -rf /`，难做细粒度权限） | 安全可控（只能调预定义接口，易在网关做隔离与审批） |
| 人类参与 | 过程像黑盒，输出给人看很凌乱 | 天然适配 UI（结果可渲染成图表、按钮） |

> 结论不是二选一，而是分工：**对高级 Agent，CLI 是最自由强大的「手脚」，MCP 是连接企业专有业务与领域知识的「标准接口」。** 未来成熟的 Agent 架构，大概率是「一个底层 Bash Tool + 若干专有业务 MCP Tools」的混合体。

## 十一、案例剖析：把 API 封装成 Agent 能力的「本地 CLI + Skills」模式

最后剖一个真实且极具代表性的架构模式：企业级平台不直接提供裸 MCP，而是提供一个**需要本地安装并登录的 CLI 工具**，安装后它往宿主应用里注册了一批「Skills（技能）」。这背后的工程考量，几乎是「企业系统接入 Agent」的最佳实践模板。

它的本质是：**用本地 CLI 把自己包装成一个强大的本地 MCP Server，并把内部的「Skills」映射成宿主应用眼中的「Tools」。** 而选择「先把 API 封装成高层 Skills 再喂给 Agent」而非直接暴露裸接口，是为了解决三个痛点：

**1. 用「宏工具」降低规划难度，让调用更流畅。** 企业原生 API 粒度极细。要 Agent 完成「拉一个项目对齐群」，裸接口下要走 `查部门人员 → 拿 ID → 建群 → 拿群 ID → 拉人 → 发欢迎语` 一条极长的推理链，步骤越多，出错和幻觉概率呈指数上升。Skill 层把这些封装成一个 `create_project_group(members, project_name)`——Agent 只做一次决策，复杂编排交给后端。这正是第五节「宏工具」原则的规模化落地。

**2. 通过 Skill 元数据注入「业务常识」与调用逻辑。** 传统 API 文档里参数叫 `chat_id`、`open_id`，模型根本不知道去哪找这些 ID。注册 Skill 时，平台不只注册了函数名，还注入了详尽的语义化描述，直接告诉 Agent「更新文档前必须先调 `search_doc` 拿到 token，再把 token 传进来」——**把业务规则和边界提前「教」给模型，防它乱猜**。这就是第五节「语义化描述」原则的现实威力。

**3. 本地接管鉴权，给 Agent 一个「无菌环境」。** 企业级鉴权（多级 Token、租户隔离、刷新逻辑）简直是「大模型杀手」——一旦让 Agent 自己处理 401 和 Token 轮换，推理循环会瞬间崩溃。你在终端手动执行的那一步 `login` 极其关键：它把最脏的鉴权与网络代理工作**死死按在本地进程里**。Agent 眼中只有纯粹的业务工具，没有 Token、没有密码；实际链路是 `Agent 发业务指令 → 本地 CLI 拦截、贴上登录拿到的 Token、处理加密 → 云端`。这正是第八节「把鉴权复杂性封装在后端 / 本地代理」的教科书实现。

再往上看一层，还有平台自身的战略考量：定义一套内部 Skill 标准，意味着同一份能力既能喂给外部通用 Agent，也能无缝接入平台自家的 AI 体系和自动化工作流（一次编写、多处运行）；配合 Serverless 部署把「自建 Server」的基建成本清零；以及能返回平台特有的**富 UI 卡片**（比如一张带「通过 / 驳回」按钮的审批卡），突破纯文本交互的体验天花板——这些都是通用、克制的 MCP 协议本身给不了的。

> 这个模式提炼成一句话：**用本地 CLI 扛下「鉴权与网络代理」，用 Skills 包装「业务编排与语义说明」，最终呈现给 Agent 的，是一个干净、流畅、自带说明书的傻瓜式工具箱。** 它几乎把本文前十节的所有原则串了起来——这也是为什么它值得作为收尾。

## 收束

把这篇串成一条线：MCP 的一切设计，都源自它的接收方从「确定的代码」换成了「会推理也会幻觉的模型」。于是——描述要写给模型看（语义化），粒度要顺着模型的规划能力（宏工具），错误要引导模型自纠（AI 友好），数据要替模型省注意力（分页与截断），危险操作要有人类兜底（Human-in-the-loop），鉴权要对模型透明（封装在后端）。它不取代 API，而是给 API 套上一层让模型读得懂的语义外衣；它也不与 CLI 争高下，而是各据一端，共同构成 Agent 的手脚与接口。

看懂了这层「一切为了会推理的消费者而设计」的底层逻辑，MCP 的每一个看似琐碎的规范细节，都会变得顺理成章。
