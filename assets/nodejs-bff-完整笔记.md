# 一、BFF 是什么:定位、角色与边界

## 1.1 场景锚点:资产首页背后的扇出

用户打开「我的资产」首页,看到的是:总资产、今日收益、持仓列表(每个产品带实时净值)、未读消息红点、底部推荐 banner。看起来一个页面,后端却是拆开的微服务:

- `account-service`:账户信息、客户风险等级(C1~C5)
- `position-service`:持仓列表
- `quote-service`:实时净值 / 行情
- `pnl-service`:收益计算
- `marketing-service`:推荐产品、banner
- `message-service`:未读消息数

如果让客户端自己调,就是 6 次请求 + 客户端拼装 + 客户端各自处理「行情挂了怎么办」,三端各写一遍。BFF 的第一个价值就在这:**把这 6 个下游收敛成一个 `GET /home/assets`,容错和编排只在服务端写一次。**

三端(网页网厅 / 移动 App / 微信小程序)加上 BFF,都是**前端团队**负责的;六个微服务是后端团队的。这条所有权边界,是 BFF 模式成立的前提。

## 1.2 BFF vs API 网关 vs 后端服务

面对「BFF 不就是个 API 网关吗?裁剪、聚合、鉴权网关都能干」的质疑,**「裁剪响应」这个理由撑不住**——因为它说的是**能力**,而能力不是分界线。网关也能配响应转换插件裁字段。只要你给的理由是「某件事 BFF 能做」,对方永远能回「网关也能做」。

真正的分界不在「能不能做」,而在两件事:**① 那里装的是哪一类逻辑;② 那块代码跟着谁的变化而变。**

一刀切下去的分界线:

> **网关不理解载荷,它只管流量;BFF 存在的全部理由,就是去理解某一个客户端、专门为它塑形载荷。**

- **网关**是横向的、通用的基础设施:TLS 终止、路由、限流、令牌校验、日志、CORS。本质特征是**它不知道也不关心响应里是什么意思**,对所有客户端一视同仁。它被「配置」出来(声明式插件),归平台/基础设施团队,在「基础设施策略」变化时才改。
- **BFF**是纵向的、产品体验专属的:为这一屏调哪 6 个服务、怎么把持仓和行情 join 成一个视图模型、iOS 首页要什么形状而小程序要什么形状、C2 客户看 R4 产品要置灰。本质特征是**它恰恰需要理解载荷的含义,因为它和某一个前端的需求绑死**。它被「编程」出来(有测试、有发布流水线的服务),归前端团队,在「那个前端的产品需求」变化时才改。

「裁剪」为什么不够:裁字段是塑形里最机械的一端,网关确实能干。BFF 真正的活是网关装不下的:**编排**(并行扇出、部分失败按客户端降级)、**跨服务组装**(持仓+行情+收益拼成一个视图)、**客户端专属展示逻辑**(脱敏、置灰、按端 i18n)、**有状态的协议适配**(Web 端 token 存服务端、小程序 code→session 换取)。这些都不是「配条规则」,是会随某个前端一起演进的代码。

### 三者各就各位

| 维度 | API 网关 | BFF | 领域/后端服务 |
|---|---|---|---|
| 围绕什么组织 | 流量 | 某个客户端的体验 | 某项业务能力 |
| 知不知道载荷含义 | 不知道(也不该知道) | **必须知道** | 知道,但客户端无关 |
| 数量 | 一个,服务所有人 | **每端一个** | 按业务域划分 |
| 归属 | 平台/基础设施团队 | **前端团队** | 后端团队 |
| 怎么造出来的 | 配置 | 编程 | 编程 |
| 拥有业务数据吗 | 否 | **否**(无 source of truth) | **是**(source of truth) |
| 随谁变 | 基础设施策略 | 某前端的产品需求 | 业务规则 |

## 1.3 为什么塑形逻辑放共享网关里会腐烂

把客户端专属的塑形逻辑塞进一个**所有人共享**的网关,会出三个问题:

1. **它会变成谁都不敢动的神级对象。** 一个共享层服务所有端,就堆满 `if (client==web){…} else if (client==mp){…}`,最后烂成一个没人拥有、人人害怕的分布式单体——这正是 BFF 被发明出来要逃离的困境。每端一个 BFF,每个才能保持小而内聚。
2. **它把团队变成彼此的阻塞。** 组件的归属边界应该和会去改它的团队边界重合(**康威定律**)。塑形逻辑放共享网关,意味着 Web 团队改个首页形状,要去碰小程序、App、基础设施团队都依赖的共享件——一次产品微调变成跨团队协调。每端一个、归前端自己,改自己的不惊动任何人。这个「自己拥有、按自己节奏发布」的能力,就是 BFF 存在的全部意义。
3. **能转换 ≠ 该由它转换。** 声明式插件适合无状态、通用、单请求的规则。一旦你的「转换」需要再调一个服务、处理一次超时、把两个响应 join、按业务规则置灰——你已经长出了网关配置装不下的东西,你需要的是能写代码、能测试、能灰度的环境。**那就是个服务,不是个插件。**

## 1.4 BFF vs 普通后端服务,以及腐化信号

普通后端服务围绕**业务能力**组织(账户、订单、支付),且天然**客户端无关**——谁来调都给同一份,它持有事实来源。BFF 围绕**客户端/体验**组织,刻意客户端**专属**;它**不拥有任何业务数据、不持有任何 source of truth**,是可丢弃、可复制的薄层。

**腐化信号:如果业务规则开始往 BFF 里钻——它自己算钱、自己定适当性规则、自己连数据库——那它就不再是 BFF 了,正在退化成又一个普通后端。** BFF 一旦开始持有「只有它知道的事实」,边界就破了。

## 1.5 它们是叠层,不是二选一

```
客户端 → API 网关(通用·流量·基础设施)→ BFF(专属·编排塑形·前端团队)→ 领域服务(业务·事实来源)
```

网关和 BFF 不是竞品,是同一条链上不同层各干各的活。网关在门口管「所有进来的流量怎么被通用地处理」,BFF 在网关之后管「这一个客户端这一屏到底要什么」。

### 一句话带走

- 网关管**流量**,BFF 管**某个客户端的体验**。
- 网关是**配置**出来的,BFF 是**编程**出来的。
- 网关**一个、服务所有人**;BFF **每端一个、归属那端的前端团队**——而这个归属,就是它存在的理由。

# 二、BFF 怎么切:聚合粒度的五把尺子

## 2.1 先扭正框架:不是「几个 vs 一个」,是「在哪下刀」

常见的错误问法是「该开一个 `/home` 还是拆成 3 个」。真正的问题是:**在哪里下刀,把页面切成几个「取数组」。** 聚合(一个 endpoint 内并行扇出 + 降级)和拆分(多个 endpoint)**可以叠加**:你先把页面切成几组,每一组内部该聚合的照样聚合。

正确的姿势:**先分组,后定实现。** 别从实现(分页?WebSocket?长连接?)往回看,那样是零散的;先拿尺子量数据的固有属性,量出来的「属性指纹」相同的归一组,不同的分家,实现方式是分完组后自然掉出来的结果。

## 2.2 五把尺子(下刀的依据)

默认是**合并**(能放一个 endpoint 就放一个,省往返)。只有当某块数据在下面几条上和其它块「节奏不同」时,才切出去:

1. **变化频率 / 新鲜度** —— 它多久变一次?
   机理:**一个聚合响应的可缓存性 = 它最易变成员的可缓存性。** 把每秒变的净值塞进 `/home`,整个 `/home` 永不可缓存,账户、banner 本可缓存的能力全被废掉。
2. **延迟 + 首屏位置** —— 它快还是慢?在折叠线以上还是以下?
   机理:**单 endpoint 的耗时 = 最慢成员的耗时。** 慢 + 折叠线下 = 它没资格占用首屏的时间预算。
3. **刷新节奏** —— 它会被**独立**重新拉取吗?
   机理:绑在一起就只能一起刷。你不会为了刷新每秒的净值,把账户信息每秒也重拉一遍。
4. **复用范围** —— 只有这一屏要,还是别的屏也要?
   机理:红点几乎每个页面都有 → 它该是全局 `/badges`,而不是首页私有字段。
5. **一致性要求(方向相反,把数据往一起拽)** —— 这几块必须是同一时刻的快照吗?
   机理:总资产和加起来等于它的那批持仓必须同一瞬间。这种跨服务 join + 一致性,**必须在 BFF 一个 endpoint 里算好**,绝不能让客户端分两次拉再自己加。

**前四把尺子是「找不同就切开」,第五把是「够一致就合并」——它们互相拉扯,平衡点就是下刀处。**

## 2.3 worked example:资产首页切成几组

| 数据块 | 变化频率 | 延迟/位置 | 刷新 | 复用 | 一致性 |
|---|---|---|---|---|---|
| 总资产+收益 | 分钟级 | 快·首屏 | 随页 | 仅此屏 | **要和持仓一致** |
| 持仓列表(静态) | 分钟级 | 快·首屏 | 随页 | 仅此屏 | **要和总资产一致** |
| 实时净值 | **每秒** | —— | **独立·秒级** | —— | 容忍短暂滞后 |
| 营销+推荐 | 天级 | **慢·折叠下** | 独立 | 仅此屏 | 无 |
| 消息红点 | 事件触发 | 快 | **独立轮询** | **全 App** | 无 |

分组是「看出来」的,不是「想出来」的:

- **总资产 + 收益 + 持仓(静态)**:五把尺子几乎一致,且第⑤把把它们焊在一起 → **同一个聚合 endpoint** `GET /home/summary`,内部并行扇出、按关键/非关键降级。
- **实时净值**:①每秒变 + ③独立秒级刷新 → **拆出去,因为「每秒推」这个特征,实现自然是 WebSocket / SSE 推送**,不是 REST endpoint。
- **营销 + 推荐**:②慢 + 折叠线下 → **拆成 `/home/feed` 懒加载**。
- **红点**:④全 App 复用 + ③独立轮询 → **全局 `/badges`**,不归首页。

> 注意:实现(REST / WS / 懒加载)是被尺子量出来的,不是一开始拍的。分组依据是数据的**固有属性**,和技术栈无关——换任何新页面都能拿这五把尺子重新量一遍。

## 2.4 降级 vs 拆分:解决两件不同的事

最容易混的一点:

- **区分关键/非关键 + 降级**,解决的是「同组成员可能失败」。这几块本该一起出现在屏幕上,但某个下游可能挂——所以容忍它缺席(收益显示 `--`、行情用昨日净值兜底)。它们节奏相同,只是可靠性不同。
- **拆分 endpoint**,解决的是「不同块节奏不同」。缓存、延迟、刷新、传输方式不一样,不该挤在同一次请求里。

判断某块是「留在聚合里降级」还是「拆出去」,支点是**它在折叠线的哪一侧**:营销 banner 是典型的「慢 + 非关键」,若在首屏可见区 → 留下来降级(设 200ms 超时,超了返回空);若在折叠线以下 → 拆出去懒加载(反正用户没滚到,且懒加载能拿完整数据而非降级后的空)。

## 2.5 中间路线:不拆,但流式返回

如果拆 `feed` 的唯一理由是「它慢、拖首屏」,还有第三条路:**单 endpoint + 流式渐进返回**(HTTP 分块 / SSE / GraphQL 的 `@defer`)。一次请求、一个往返,快的部分先吐给客户端渲染首屏,慢的随后补流进来。

但金融多端有现实约束:**微信小程序对流式响应支持很弱**(没有 SSE,`request` 分块响应受限,只有 WebSocket 能用且需域名白名单)。所以这条路在 Web/App 上漂亮,在小程序上多半还得退回「summary 折叠以上 + feed 懒加载」的拆分。

## 2.6 反模式

- **别按微服务边界拆 endpoint。** 给每个下游配一个 BFF endpoint(`/account`、`/position`…让客户端调 6 个)是错的——等于把后端拓扑泄露给客户端,聚合价值荡然无存,还把「部分失败怎么办」的编排推给三端各写一遍。**按客户端的渲染/缓存/刷新需求切,不是按后端服务切。**
- **别一个超级 endpoint 装下整个 App。** 那样耦合一切、不可缓存、慢如最慢成员。

### 一句话尺子

> **一起取、一起缓存、一起刷新、一起失败、且必须一致 → 合并进一个 endpoint(内部并行扇出+降级);这几条里任意一条分道扬镳 → 拆开。实现方式是分完组后自然掉出来的,不是分组的依据。**

# 三、BFF 的容错:为什么「慢」比「挂」更可怕

## 3.1 故障现场

资产首页 `GET /home/summary` 内部并行扇出,营销服务非关键,已经用 `Promise.allSettled` 做了降级(失败返回空 banner)。某天凌晨三点:

- 整个资产首页 **P99 从 200ms 飙到 8 秒**,大量用户白屏、转圈、超时。
- 账户、持仓、收益服务全正常。
- 只有营销服务**变慢了**——它**没挂、没报错**,响应从 50ms 涨到 8 秒,但最终还是规规矩矩返回 200。

一个「非关键、且已做降级」的下游,仅仅是**变慢**(没挂),为什么能把整个首页拖垮?

## 3.2 题眼:Node 运行模型 + 资源耗尽型级联

### Node 不是「一请求一线程」

很多人的并发模型是「一请求一线程」(Java/Go 直觉):线程卡住只卡它自己。**Node 完全不是。** Node 是**单线程事件循环**处理所有 JS,成千上万并发请求跑在同一线程上。它扛高并发靠的不是多线程,而是**「没人傻等」**:遇到 I/O 就 `await` 挂起、让出线程。命根子一句话:

> **没有任何一个请求可以「占着线程干等」,所有等待都必须是「挂起让位」式的。**

`await fetch(营销)` 确实挂起让位了,线程没被占住。**但「线程没被占住」不等于「什么都没被占住」。**

### 一个请求卡 8 秒,赖着不放的是什么

`await fetch(营销)` 挂起的瞬间,这个请求整个上下文悬在半空,持续占用:

- **一个出站 socket / 连接池里的一个连接**(连营销那条)——响应没回,不能还。
- **入站那条 HTTP 连接**(客户端到 BFF)——首页没拼完,不能关。
- **内存里这个请求的全部上下文**——闭包、已拿回的账户/持仓数据、待执行回调。
- **事件循环里一个待决回调。**

### 把「一个慢」放大成「全站雪崩」

- 正常时,营销 50ms 返回。任意一刻悬在半空等营销的请求数 ≈ `500/s × 0.05s = 25` 个,毫无压力。
- 变慢到 8 秒后,同样 500/s 涌入,每个赖 8 秒才走。悬在半空的请求数 ≈ `500/s × 8s = 4000` 个,且持续往上堆。

这 4000+「僵尸请求」虽没占线程,却把**有限的进程级共享资源**一个个抽干:

1. **连接池先爆。** 连营销的 HTTP 连接池(假设上限 100)被占满,第 101 个请求卡在「等一个连接」上,**根本还没发出请求**。
2. **入站侧。** 4000 个请求各攥一条客户端到 BFF 的连接,**文件描述符(fd)、入站连接数**被撑满。
3. **内存涨。** 4000 个上下文悬在堆上,内存爬升,触发频繁 GC,GC 又拖慢一切,正反馈。
4. **新用户彻底进不来。** 一个全新请求第一步要调账户服务,可此时连接池、fd、内存全被「等营销的僵尸」占满,**它连给账户服务发请求的资源都申请不到**。

最毒的地方:**账户、持仓、收益服务从头到尾健康,但新用户连碰都碰不到了。** 一个非关键下游的「慢」,通过**全进程共享的有限资源**,把整个 BFF 进程对所有用户拖瘫。

### 两个该说出口的名字

- 被耗尽的资源:**连接池 / 文件描述符 / 内存 / 事件循环积压**——统称**进程级共享资源**。Node 的少线程模型让它对「请求堆积」格外脆弱,因为没有「一请求一线程」的物理隔离。
- 现象的名字:**资源耗尽型级联故障(cascading failure)**,这条路径常被叫**连接池耗尽**;源头(一个慢依赖把上游资源占住)就是经典的 **slow dependency / head-of-line blocking**。

### 慢 vs 挂,一句话钉死

- **挂(快速失败):** 营销一连接就 `ECONNREFUSED`,请求 5ms 内拿到失败终态,立刻释放资源走人,降级接管。资源占用 ≈ 0。
- **慢(迟迟不失败):** 营销赖着资源 8 秒才给终态。占用时间是挂掉的 1600 倍,请求像血栓一样堆积,堵死共享池。

> **快速失败是系统的安全阀;一个「慢而不挂」的依赖,等于把安全阀焊死了。**

## 3.3 四层防御

### ① 超时(timeout):把「慢」强行变成「失败」

唯一使命:把「慢」转成「快速失败」,让降级有机会触发。**没有超时,「慢」永远不变成「失败」,降级逻辑永远不被调用。**

**致命的坑:到点必须真正取消底层请求、把 socket 还回池。**

```js
// ✅ 正确:AbortSignal.timeout 到点会真正 abort 底层 socket,释放连接
const res = await fetch(url, { signal: AbortSignal.timeout(500) });

// ❌ 假超时:Promise.race 看起来 500ms 就返回了,
// 但底层那个 fetch 根本没被取消,socket 照样占满 8 秒!
await Promise.race([fetch(url), rejectAfter(500)]);
```

`Promise.race` 让**你的代码**以为超时了,可**底层连接没释放**——你以为挡住了雪崩,实际那条 socket 还在耗满 8 秒。**超时的本质是「释放资源」,一个不取消底层请求的超时等于没加。**

参数:按每个下游的 **p99 + 余量**单独设(营销 p99 50ms → 300~500ms),不要一个巨大的全局超时。

局限:就算每个 500ms 超时,`500 rps × 0.5s = 250` 个并发还卡在那 500ms 上。超时**缩短**了占用,没**消除**占用,所以只是第一层。

### ② 熔断(circuit breaker):有记忆,踩过坑就不让后面的人再踩

类比就在名字里:家里配电箱的**空气开关**。电流持续过载就**跳闸**断电保护房子,过一阵再**试探性合闸**。

和超时的本质区别:**它有记忆。** 超时是「每个请求各自吃一次亏」(250 个并发各等各的 500ms);熔断是「**吃过一次亏就不让后面的再吃**」(失败率超阈值就跳闸,后续请求根本不发给营销、直接走降级)。这就是它治雪崩的关键——跳闸后那 250 个本该卡在营销连接池上的请求**压根不会产生**,营销那个池占用瞬间归零,从**源头**掐断占用。

**三状态机(核心):**

| 状态 | 行为 | 转移 |
|---|---|---|
| 关闭 Closed | 正常放行,统计失败率 | 失败率超阈值 → 打开 |
| 打开 Open | 快速失败 / 直接走降级,不碰下游 | 冷却(resetTimeout)到期 → 半开 |
| 半开 Half-Open | 放行少量试探请求 | 试探成功 → 关闭;试探失败 → 打开 |

**Half-Open 是关键:它让系统在下游恢复后自动合闸,不需要人半夜爬起来手动重启。**

实现(`opossum`,把超时 + 熔断 + 降级打包):

```js
import CircuitBreaker from 'opossum';

const breaker = new CircuitBreaker(callMarketing, {
  timeout: 500,                 // 内置超时:500ms 没回就算一次失败
  errorThresholdPercentage: 50, // 窗口内失败率 > 50% → 跳闸(Closed→Open)
  resetTimeout: 10_000,         // 跳闸后 10s 进入 Half-Open 试探
  volumeThreshold: 20,          // 窗口内至少 20 个请求才统计(防冷启动/低流量误判)
});
breaker.fallback(() => ({ banners: [] })); // 降级:Open 态或失败时直接返回空 banner

const data = await breaker.fire(userId);   // Open 态时,这行根本不碰营销,直接给 fallback
```

`volumeThreshold` 很重要:没它的话,低流量时来 1 个失败 1 个就是 100% 失败率,会被误判跳闸。

### ③ 隔离(bulkhead):给每个下游独立的舱

类比:轮船的**水密舱壁**。一个舱破了,水漫不到全船。给每个下游**单独一套资源配额**(独立连接池 / 独立并发上限),营销把它自己那套占满了,**账户、持仓用的是另一套池子,永远抽不到它们头上**。它把「全进程共享资源 = 病毒传播路径」**物理切断**,是最对症的一层。

第一层,每个下游独立连接池:

```js
import { Agent } from 'undici';

// 营销专用舱:最多 50 条连接,占满也只占满这 50
const marketingAgent = new Agent({ connections: 50, keepAliveTimeout: 10_000 });
// 账户专用舱:独立的 100 条,和营销互不干扰
const accountAgent = new Agent({ connections: 100, keepAliveTimeout: 10_000 });

await fetch(marketingUrl, { dispatcher: marketingAgent, signal: AbortSignal.timeout(500) });
```

第二层(可选),应用层并发上限:

```js
import pLimit from 'p-limit';
const marketingLimit = pLimit(20); // 营销最多 20 个在途
await marketingLimit(() => callMarketing(userId));
```

坑:`p-limit` 满了之后是**排队**,而**队列本身也是资源**——无限排队等于换个地方堆积。真正的 bulkhead 语义应该是「满了就立即放弃、走降级」。实践中,**独立连接池 + 熔断**通常就够,并发上限是给特别需要硬隔离的关键路径加的保险。

### ④ 降级(fallback):备胎,但它是最后一道

前三层把「慢」挡成了「快速失败 / 直接跳过」,降级负责接住失败、返回可接受的替代品。常见形态:静态默认值(空 banner)、上一次缓存值(行情挂了用昨日净值)、降质结果(个性化推荐挂了返回热门兜底列表)。

多个下游聚合时用 `allSettled` 兜住部分失败:

```js
const [acc, pos, mkt] = await Promise.allSettled([
  accountBreaker.fire(uid),
  positionBreaker.fire(uid),
  marketingBreaker.fire(uid), // 它内部已 fallback,这里基本不会 rejected
]);
```

三个一定要说的坑:

1. **降级逻辑必须本地、便宜、可靠。** 别让兜底再去调另一个会抖的服务——**会失败的兜底不叫兜底**。
2. **只给非关键下游降级。** 账户是关键下游,**绝不能给它一个「假装成功」的兜底**(返回空账户会吓死用户)。关键下游正确处理是:熔断让它快速失败,然后整页明确报错。
3. **降级只有在前三层生效后才轮得到。** 没有超时把「慢」转成「失败」,降级永远不触发——这就是开头那个 `allSettled` 没救场的原因:只写了第 4 层,前 3 层全缺。

## 3.4 组合顺序与统一客户端

包裹顺序固定——**降级在最外(catch 一切),熔断包着真正的调用,调用自带超时、且跑在自己的隔离池上**:

```
fallback( breaker( timeout( call_on_bulkhead_pool ) ) )
```

封装成工厂,每个下游一个实例,各自的池、各自的熔断器:

```js
import CircuitBreaker from 'opossum';
import { Agent } from 'undici';

function createClient({ name, baseUrl, timeout, poolSize, fallback }) {
  const agent = new Agent({ connections: poolSize, keepAliveTimeout: 10_000 }); // 隔离

  async function call(path) {
    const res = await fetch(baseUrl + path, {
      dispatcher: agent,
      signal: AbortSignal.timeout(timeout), // 超时:真正 abort,释放连接
    });
    if (!res.ok) throw new Error(`${name} ${res.status}`);
    return res.json();
  }

  const breaker = new CircuitBreaker(call, {        // 熔断
    timeout: timeout + 100,
    errorThresholdPercentage: 50,
    resetTimeout: 10_000,
    volumeThreshold: 20,
  });
  if (fallback !== undefined) breaker.fallback(() => fallback); // 降级(关键下游不给)

  return (path) => breaker.fire(path);
}

// 非关键:给兜底
const marketing = createClient({ name: 'marketing', baseUrl: MKT, timeout: 500, poolSize: 50, fallback: { banners: [] } });
// 关键:不给兜底,让它快速失败、整页明确报错
const account  = createClient({ name: 'account',  baseUrl: ACC, timeout: 800, poolSize: 100 });
```

## 3.5 每层切级联链的哪一环

- **超时** → 把「赖 8 秒」砍成「赖 500ms」,**缩短**单请求占用时长。
- **隔离** → 营销占满的只是它自己那 50 条,**物理切断**共享传播路径。
- **熔断** → 跳闸后请求根本不进营销链,**从源头**让占用归零(治雪崩主力)。
- **降级** → 把前三层造出的「快速失败」**翻译**成空 banner,用户无感。

> 客户端超时是**用户体验自保**:客户端 3 秒断开,但 BFF 进程里那个请求还在赖着营销 8 秒,资源照占——所以它对进程级雪崩**毫无帮助**。

### 一句话锁死

> **在 Node 里杀死你的从来不是「下游挂了」,而是「下游慢而不挂」——它让请求赖在共享的进程级资源(连接池/fd/内存)上不释放,堆积成资源耗尽型级联故障。防御的本质是两件事:缩短占用(超时)、切断共享(熔断 + 隔离);降级只是最后收尾。**

# 四、底层网络:慢请求如何耗尽资源

## 4.1 socket = TCP 连接 = fd(同一根管子的三个剖面)

「socket」「TCP 连接」「连接池里的一个连接」指的是**同一根物理管子**,只是站在三个层各叫一个名字:

```
HTTP 连接   ← 应用层:在这条管子上跑的「请求/响应」对话
   ↑ 跑在
TCP 连接    ← 传输层:由四元组(源IP:源端口 → 目标IP:目标端口)唯一确定的那条管子
   ↑ 操作系统给你的把手是
socket / fd ← OS 层:你在代码里拿到的句柄。Linux 上 socket 就是一个文件描述符(fd)
```

HTTP 不是另一条连接,它是**寄生在那条 TCP 连接上的对话**(HTTPS 中间还垫一层 TLS 会话,同样跑在这条 TCP 上)。

## 4.2 为什么 HTTP/1.1 下慢请求占住连接

HTTP/1.1 的铁律:**一条 TCP 连接同一时刻只能跑一个请求/响应,响应没收完,这条连接不能复用、也不能还回池子。**

所以营销慢吞吞 8 秒返回时,那条 BFF→营销 的 TCP 连接,从「请求发出」到「响应完整收到」的整整 8 秒被这一个请求独占,既不能跑别的营销请求,也不能 keep-alive 还回池。**「慢」占资源的物理实质:它把 TCP 连接钉在「已建立但用不了」的状态上 8 秒。** 而「挂」是连接根本没建起来,5ms 就失败释放。

## 4.3 连接池 / fd / 端口三道墙

「连接池被占满」和「fd 被耗尽」不是两个独立故障,是**同一批被钉住的 TCP 连接在两个层面同时撞上限**:

- **应用/连接池视角**:数「几条到营销的连接」(`maxSockets` / `connections`)。
- **操作系统视角**:每条 TCP 连接(无论入站出站)占用进程一个 **fd**,进程 fd 总数有硬上限(`ulimit -n`)。

出站每多钉一条连营销的连接 = 多占一个 fd,此外还吃掉一个**本机临时端口**(Linux 默认约 2.8 万个)。入站、出站本质一样(都是 TCP / fd),只是「被占住的理由」不同:出站是营销响应没回,入站是首页没拼完、给客户端的响应发不出去。

## 4.4 keep-alive

### 没有它的世界:每个请求都重建 TCP

建一条 TCP 连接本身有昂贵开销。没有 keep-alive(HTTP/1.0 默认),每发一个 HTTP 请求都要走:

```
① TCP 三次握手(1 个 RTT)
② TLS 握手(HTTPS,再 1~2 个 RTT)
③ 发请求、收响应
④ TCP 四次挥手,连接关闭、销毁
   —— 下一个请求回到 ①,从头再来
```

真正传数据的 ③ 可能只要几毫秒,但前面握手白搭进去一两个 RTT。放到「一个首页扇出 6 个下游」的聚合场景,每次扇出 = 6 次全新握手,延迟被握手成本主导。更糟的是海量短命连接关闭后进入 TCP `TIME_WAIT`(滞留约 2×MSL,几十秒到 1 分钟),堆积会**吃光临时端口**,最后连新连接都建不出来。

### 它在做的事

> **keep-alive 让一条 TCP 连接在一次请求/响应结束后不立即关闭,而是留着给下一个请求复用。** 握手只在第一次付一次钱,后面成百上千个请求共享这条已建好的连接。

它也叫**持久连接**,在 HTTP/1.1 里是**默认行为**(除非 `Connection: close`)。

### 与连接池绑死(最容易混的点)

**keep-alive 让连接「可复用」,连接池是那个「存放可复用连接、并把它们分配出去」的容器。没有连接池,keep-alive 几乎没用武之地。** 它俩是一套机制的两半:

- **keep-alive** 负责:用完别关,留着。
- **连接池** 负责:把这些留着的连接存起来、管理、复用——下个请求先从池里捞一条空闲的现成连接,捞不到才新建。

前面说「连接池里的一个连接被慢请求占住不还」,那个「还」字,还的就是 keep-alive 的连接池。**慢请求破坏的正是这个「用完归还」的循环。**

### Node 实操(默认值是坑)

```js
// 原生 http:历史默认 keepAlive: false,每个请求都在重建连接!必须显式开
import http from 'node:http';
const agent = new http.Agent({
  keepAlive: true,
  maxSockets: 100,        // 这条线路最多 100 条可复用连接(隔离/池大小)
  keepAliveMsecs: 30_000, // 空闲连接每隔 30s 发 TCP keep-alive 探测包保活
});

// undici(Node 全局 fetch 的底层):默认就开 keep-alive
import { Agent } from 'undici';
const agent2 = new Agent({
  connections: 100,          // 池大小(每个 origin)
  keepAliveTimeout: 30_000,  // 一条连接空闲多久后关闭
  keepAliveMaxTimeout: 600_000,
});
```

### keepAliveTimeout 两端必须协调(经典暗坑)

连接留着复用,总得有「空闲多久没人用就关掉」的超时,而这个超时**两端各有一个**。如果**下游服务器的超时比你 BFF 的短**:下游已悄悄关了连接,但 BFF 以为它还活着,捞出来就发请求 → 撞上对方的关闭 → `ECONNRESET`,请求莫名失败(偶发、无规律,极难排查)。

**经验法则:让客户端(BFF)侧的空闲超时略小于服务端侧**,保证「要关也是我这边先主动关、用一条干净连接」。(这也是当年 Node 服务器默认 `keepAliveTimeout` 5s、容易和上游 ALB/Nginx 默认 60s 打架的著名坑的根源。)

## 4.5 RTT

> **RTT(Round-Trip Time,往返时延)= 一个数据包从你发出、到对端、再把回应送回来,这一个来回所花的时间。**

它量的是**来回**,因为网络通信几乎都是一来一回的对话,你能直接测到(一个 `ping`)、也真正影响你的就是这个来回。

它主要由**物理距离 + 网络路径**决定,**和数据量基本无关**——哪怕只发 1 个字节也得等一个完整来回。它是一种**固定的「路费」**,每次往返都付:

| 场景 | RTT 量级 |
|---|---|
| 同机房内 | < 1ms |
| 同城不同机房 | 1~3ms |
| 国内跨地域(京↔深) | ~30ms |
| 跨洲(中↔美) | ~150~200ms |

把它接回 keep-alive:握手贵,是因为它要额外付好几个 RTT(三次握手 1 个 + TLS 1~2 个)。假设 RTT = 30ms,不用 keep-alive 每个请求 ≈ 4 个 RTT ≈ 120ms,其中 ~90ms 全耗在握手这个「路费」上;用 keep-alive,握手只第一次付,后续 ≈ 30ms。**握手成本按 RTT 计,而 RTT 是省不掉的固定路费,所以唯一优化就是别反复付。**

## 4.6 HTTP/2 的差别(级联不消失,只换上限)

HTTP/2 一条 TCP 连接能**多路复用**几十上百个并发流(stream),不再一请求一连接,所以你可能不会先以「连接池耗尽」的形式倒下。但级联**不会消失**,只是换个上限先撞:HTTP/2 每条连接有 `MAX_CONCURRENT_STREAMS` 上限(常见 ~100),撞满照样阻塞;每个卡住的请求该占的内存、上下文、入站连接、回调一样都没省。

> **无论 HTTP/1.1 还是 HTTP/2,「慢请求赖着共享资源不放」这个本质不变,变的只是你先用光哪一种资源。**

# 五、认证:JWT / Session / Cookie 与 better-auth

> 本节关于 better-auth 的具体行为来自其官方文档(见文末参考链接),整理时已核对。

## 5.1 解锁点:这三个词在两条垂直的轴上

混淆来自把它们摆成「三选一」。错。它们分属两条互相垂直的轴:

- **Cookie 是「运输方式」**——只回答「凭证怎么在浏览器和服务器之间携带」。本质是一个 HTTP 头机制:服务器 `Set-Cookie` 下发,浏览器之后**自动**在每个请求带上。它**不关心**你装进去的是什么。
- **Session vs JWT 是「策略」**——回答「凭证里装什么、关于你的真相存在哪」:
  - **Session(有状态)**:凭证是**无意义的随机 id**,真相全在**服务端存储**。
  - **JWT(无状态)**:凭证**自带身份信息**,用签名防篡改,真相**写在 token 自己身上**,服务端不查库。

**两条轴垂直、自由组合**,四个格子全成立:

| 运输 \ 策略 | Session(真相在服务端) | JWT(真相在 token 自身) |
|---|---|---|
| **Cookie**(浏览器自动带) | 传统会话,**better-auth 默认(Web)** | cookie 里装 JWT(如 cookieCache 的 jwt 策略) |
| **Bearer**(客户端手动带) | header 带 session id(better-auth bearer · 移动端) | 经典 Bearer JWT(`Authorization: Bearer …`) |

## 5.2 完整流程:以 better-auth 默认(Cookie × Session)走一遍

**① 登录(签发会话)。** 验证凭证(查用户表、比对密码哈希)→ 通过后在 **session 表建一条记录**(含 session token、userId、过期时间)→ `Set-Cookie` 把 **session token** 下发给浏览器。cookie 里装的不是用户信息,只是指向 session 行的「无意义钥匙」。

cookie 安全属性正是「BFF 安全模式」那套:better-auth 的所有 cookie 都用密钥签名,生产环境默认带 `httpOnly` 和 `secure`,会话 cookie 默认 `SameSite=Lax`。`httpOnly` 让前端 JS 读不到(防 XSS 窃取),`Secure` 强制 HTTPS,`SameSite` 防 CSRF——**真相(身份)在服务端,浏览器只攥着一把 httpOnly 钥匙。**

**② 后续请求(校验)。** 浏览器自动带 cookie → 服务端取出 session token → **查 session 表** → 存在且未过期 → 放行,加载用户。

**③ 滑动过期。** 会话默认 7 天过期;每次使用若达到 `updateAge` 阈值(默认 1 天),过期时间顺延。活跃用户不被平白踢掉,长期不用的自然失效。

**④ 登出 / 吊销(session 的看家本领)。** 真相在服务端那张表里,**登出 = 删掉那条 session 行**;下个请求一查「没这条了」,**当场失效**。挂失、远程下线都靠它。这就是「session 的吊销是免费的,因为它每次本来就要查库」。

## 5.3 cookie cache:性能 ↔ 即时吊销的旋钮

每个请求都查一次 DB 贵不贵?better-auth 的优化:**开启 cookie 缓存后,服务端直接从 cookie 本身校验会话有效性,而不必每次查库;cookie 被签名防篡改,用一个较短的 `maxAge` 保证数据定期刷新。** 缓存可用三种策略编码:`compact`(HMAC-SHA256 签名)、`jwt`(HS256 签发 JWT)、`jwe`(加密)。

> 矩阵里「Cookie 里装 JWT」那格,在 better-auth 里就是 cookie cache 的 jwt 策略:一个临时的、自包含的 JWT,贴在 session 之上当性能缓存。

代价:**被吊销的会话在其它设备上可能仍然有效,直到该设备的 cookie 缓存按 `maxAge` 过期为止**(缓存数据存在客户端浏览器,服务端无法直接删掉其它设备上的 cookie)。

**这就是一个可调的旋钮:**

- 纯 session(不开 cache)= 每请求查库、**可即时吊销**。
- 开 cookie cache = 不查库、**快**,但吊销有最多 `maxAge` 的延迟。

挂失这种强即时场景就把 `maxAge` 调小甚至关掉 cache;普通场景就放宽。**这正是「性能 vs 即时吊销」二选一被做成一个旋钮。**

## 5.4 纯无状态与 JWT plugin

往无状态推到底:**不配数据库时,better-auth 自动进入无状态模式**,会话数据存在签名/加密的 cookie 里,服务端从不查库、只验签和过期。这就是纯无状态的代价兑现——**快,但难即时吊销**。

> 补「即时吊销」的通用手法(不退回 session):给无状态验签挂一道 **O(1) 的吊销检查**——token 黑名单(把 `jti` 写进 Redis,TTL = token 剩余寿命),或更适合「全端下线」的**用户级失效时间戳**(`revokeBefore:{userId}` 记一个时刻,签发时间早于它的 token 全部作废)。每个请求只问一个布尔问题,绝大多数答案是「不在」直接放行,远比「查完整 session」轻。

better-auth 的 **JWT plugin** 是另一回事:它给你的 BFF / 微服务签发 JWT,让下游无状态地验证身份。**别把两种 JWT 用途搞混:一种是会话凭证(登录态),一种是服务间身份令牌。**

## 5.5 三端:Cookie vs Bearer 本质是「浏览器 vs 非浏览器」

矩阵的**纵轴(运输)**直接决定三端怎么分:

- **Web**:浏览器能自动带 cookie、能存 httpOnly cookie → **Cookie × Session 是绝配**,better-auth 默认 + Web BFF 安全模式天然契合。
- **App / 小程序**:**没有「浏览器自动带 cookie」这套机制**,httpOnly 无从谈起 → 走 **Bearer**:把凭证放进 `Authorization` header 手动带。better-auth 为此提供 bearer 方案,返回一个 token 让非浏览器客户端自己携带(里面装 session token 或 JWT 均可)。

> 网上吵的「Cookie 派 vs Token 派」,根子不是哪个更安全,而是**「你的客户端是不是浏览器」**:浏览器有 cookie 自动+httpOnly 的便利就用 cookie,非浏览器没有就手动带 token。

## 5.6 Cookie 模式特有的坑:CSRF

Cookie「自动携带」是便利,但正是这个自动带来了 token 模式没有的 **CSRF**:恶意站点能诱导浏览器自动带上你的 cookie 发请求。所以 cookie 模式必须额外防 CSRF,better-auth 用三道:`SameSite=Lax`、对每个请求校验 `Origin` 头是否来自可信源、用 Fetch Metadata 头(`Sec-Fetch-Site` 等)针对首次登录场景做额外防护。

而 Bearer token 因为是**手动**带、不会被浏览器自动附加,**天然不吃 CSRF**(这是 token 模式的真实优势);代价是 token 通常存在 JS 能碰到的地方,又得防 XSS。**两条轴各有各的攻击面,没有银弹。**

### 一句话

> **Cookie 是「怎么带」(运输),Session/JWT 是「装什么、真相在哪」(策略),两条轴垂直、自由组合。better-auth 默认走 Cookie × Session(真相在 DB,删行即吊销),用 cookie cache 在「查库的即时性」和「不查库的性能」之间提供一个 `maxAge` 旋钮;往无状态推到底就是纯 JWT 的取舍;而三端差异本质是纵轴上「浏览器能自动带 httpOnly cookie、非浏览器只能手动带 bearer token」。**

# 附录:贯穿全篇的判断尺

几条反复出现、能迁移到其它设计的「元原则」:

- **source of truth 归谁,边界就划在哪。** BFF 不持有任何业务事实(可丢弃、可复制);业务事实归领域服务。这条尺子在「BFF vs 后端」「认证里 BFF vs 认证服务」「BFF 能连 Redis 不能连业务 DB」里反复用到。
- **越界与否,不在于「连不连存储」,而在于「持有的东西丢了之后,是否会丢失唯一的真相」。** 丢了能重建(会话)→ 可以连 Redis;丢了真相就没了(用户表)→ 不归你。
- **先分组,后定实现。** 分组依据是数据的固有属性(频率/延迟/刷新/复用/一致性),实现(REST/WS/懒加载)是结果不是依据。
- **「慢」比「挂」可怕。** 快速失败是安全阀,慢而不挂等于焊死安全阀;防御本质是缩短占用 + 切断共享。
- **能力不是分界线。** 「某件事 X 也能做」永远反驳不了边界;真正的分界是「装哪类逻辑」和「跟着谁变」。

## 一句话清单(每篇博客的 takeaway)

1. 网关管流量、BFF 管某端体验;网关配置出来、BFF 编程出来;网关一个、BFF 每端一个,归属即理由。
2. 一起取/缓存/刷新/失败/且一致 → 合并;任一条分道扬镳 → 拆开;实现是分完组后自然掉出来的。
3. 杀死你的是「慢而不挂」;超时缩短占用、隔离切断共享、熔断掐断源头、降级收尾翻译,且必须按这个顺序叠。
4. socket = TCP 连接 = fd;HTTP/1.1 下慢请求把连接钉死;keep-alive 把握手路费从每请求一次摊成每连接一次。
5. Cookie 是运输、Session/JWT 是策略,两轴垂直;cookie cache 是「性能 vs 即时吊销」的旋钮;三端差异本质是浏览器 vs 非浏览器。
